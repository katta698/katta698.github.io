Azure Architecture Series #105 — Bastion: SKUs, Native Client and Shareable Links

Nov 26, 2026 13 min read
✓Verified against current vendor documentation on 26 November 2026. Pricing, limits and API behaviour were checked against the official docs on that date. Cloud services change fast — if you are reading this much later, treat the specifics as a starting point and re-check the linked sources.

Business Challenge

#104 was about keeping traffic apart and proving it. This post is the hole that gets cut in it on purpose: administrators still have to reach the machines. Every segmentation design eventually has to answer how, and the honest version of that answer has to survive the sentence “show me who connected to that server last Tuesday.”

Bastion is the service for this, and it is genuinely good at the part people choose it for. Connections are “RDP/SSH over TLS on port 443”, the target machines need no public IP, no agent and no special client, and the VMs are “protected from port scanning.” One deployment serves peered networks, so it is one control point rather than a jump box per environment.

Where it gets decided badly is the SKU, and for a predictable reason: the comparison page leads with concurrency numbers, so the conversation becomes “how many admins do we have?” That is the least consequential question on the page.

Two things that are easy to get wrong before anyone connects at all

Billing starts at deployment. “Billing starts from the moment Bastion is deployed, regardless of usage.” A Bastion in a rarely-touched environment costs the same as a busy one, which makes a per-environment deployment an expensive habit and peering the cheaper pattern.

The SKU ratchet only turns one way. Azure “supports upgrading from lower SKUs to higher SKUs, but downgrading isn't supported” — to go down you “must delete and recreate Azure Bastion.” Upgrades take about 10 minutes and features can be added during the process, so starting low and growing is safe. Starting high and regretting it is not.

Architecture

Capacity is one number times the instance count

The scaling model is simpler than the tables suggest. An instance is “an optimized Azure VM that is created when you configure Azure Bastion”, also called a scale unit, and per-instance capacity is 20 RDP plus 40 SSH sessions — the same on Basic, Standard and Premium. Everything else is multiplication.

Two readings of that table matter. First, Basic's 40 RDP sessions are usually plenty, so concurrency is almost never the reason to leave Basic — features are. Second, Developer's “1” is not a small capacity, it is a different product: a shared resource supporting “one VM connection at a time”, with no virtual network peering and no concurrent connections, and the documentation carries a warning that it “isn't suitable for production workloads.”

The subnet decision outlives the SKU decision

AzureBastionSubnet must be /26 or larger for anything deployed on or after 2 November 2021, must carry that exact name, must sit in the same virtual network and resource group as the host, and “can't contain other resources.” Older /27 subnets “are unaffected by this change and will continue to work” — but “using a smaller subnet space limits the number of scale units.”

So an inherited /27 is not a problem until the day you need host scaling, at which point it is the problem, and fixing it means resizing a subnet in a live virtual network. Size it /26 even on Basic, where scaling is not available, because the SKU can be upgraded later and the subnet is the harder thing to change.

Why This Architecture Holds Up

Because the convenient paths are the unaudited ones

This is the finding I would take away from the whole post. Premium exists largely for session recording — recorded graphical sessions land “in a blob container within your storage account” after the session closes, which is what satisfies an audit requirement. Premium in preview also adds SSH command logging, a text record of commands run, and RDP Vision and SSH Vision, which analyse a finished session for suspicious activity.

And then, stated plainly in the same document: “Command logging isn't currently available for native client connections”, and “because session recording isn't available for native client connections, RDP Vision doesn't analyze those sessions.”

Buying Premium does not mean sessions are recorded

The native client — connecting through the Azure CLI with the RDP or SSH client already on your laptop — is the method experienced administrators prefer, and it is the method that produces no recording, no command log, and therefore no Vision analysis. It is also the only method that supports file upload and download.

So the uncomfortable combination is real: the path with file transfer is the path with no recording. If the control you told an auditor about is session recording, then the native client has to be prevented by policy, not merely discouraged — because nothing in Bastion stops someone with Standard or Premium from using it.

The portal path, by contrast, is fully covered and can be tightened further: disabling copy and paste in the web client is a Standard-and-above feature. That gives a coherent posture for a regulated environment — portal only, clipboard disabled, recording on — at the cost of the convenience that makes administrators reach for the CLI.

Because a shareable link is an identity decision, not a networking one

Shareable links are the feature most likely to be enabled for a good reason and reviewed for a bad one. They let a user “connect to a target resource… without accessing the Azure portal”, which is exactly what you want for a vendor, an auditor or a contractor who should not be given a tenant identity.

The design is better than it first sounds. “The shareable link doesn't contain any credentials - the admin must provide sign-in credentials to the user”, so possession of the URL is not access. Links take an explicit expiry, and after it “the link can't be used to connect to the target resource”, with the status changing to Link expired. And the default IAM posture is restrictive: “By default, users in your org have only Read access to shared links” — enough to use and view, not to create or delete.

What to design around:

  • Credential delivery is yours to solve. The link is safe to email; the password is not, and Bastion has no opinion about how you send it. That channel is now part of your access control, and it is the part with no logs.
  • The ceilings are real. “Bastion only supports 500 shareable links per Bastion resource” and “only supports 50 requests, including creates and deletes, for shareable links at a time” — so filling a Bastion to its ceiling is ten batches, and bulk cleanup is batched too.
  • Visibility needs its own permission. Creation and deletion map to createShareableLinks and deleteShareableLinks actions, and without getShareableLinks “the user won't be able to see a shareable link.” A reviewer who cannot list links cannot review them.
  • Dead links persist, and that is useful. If a link stops working it means “someone in your organization has deleted that resource”; the link stays in the list and fails. The documentation suggests you may “keep it for auditing purposes”, which is the right instinct — it is evidence of what access existed.
  • Topology limits. Not supported “for peered virtual networks across tenants”, not supported “over Virtual WAN”, and no connections to on-premises or non-Azure machines. A hub-and-spoke estate on Virtual WAN cannot use this at all.

Because the protocol crossings are a Standard feature, and nobody expects that

Two rows in the SKU matrix catch people out, because they look like protocol support rather than tier gating: RDP to a Linux VM and SSH to a Windows VM are both No on Developer and Basic, and Yes only from Standard.

In a mixed estate that is a real constraint. A Windows administrator who wants SSH to a Windows box, or a Linux team running a desktop environment over RDP, needs Standard — and the requirement usually surfaces after Basic is already deployed and in use. Custom inbound ports are also Standard-only, with the defaults being 3389 for RDP and 22 for SSH; if a host listens elsewhere, that too is a tier conversation.

Because two settings are frozen at deployment

Most Bastion settings are changeable. Two are not, and both are the kind of thing discovered during a resilience review rather than during design.

Availability zones. You must deploy “using manually specified settings” and specify the zones at deployment time, because “you can't change availability zone settings after Azure Bastion is deployed.” Accepting the portal's defaults forfeits the choice. Zone support is in preview in twelve regions.

IPv6 dual stack. “Dual stack must be configured when the Bastion is created; existing IPv4-only Bastions can't be converted to dual stack.” And the scope is narrower than it reads: IPv6 covers “the connection between the user and Azure Bastion only” — the hop from Bastion to the target VM stays IPv4, IPv6-only is unsupported, and IPv6 is not supported on private-only deployments at all. So “Bastion supports IPv6” is true for the client side of one hop and nothing else.

Private-only deployment is the Premium feature that completes the segmentation story from #104: a “non-internet routable deployment of Bastion that allows only private IP address access”, with no public IP on the host at all. It is the one configuration where the administrative entry point is not reachable from the internet — and it is mutually exclusive with IPv6.

Closing Thought

The SKU table is organised by capability, and capability is the wrong axis to read it on. Read it by what survives the session instead. Developer leaves nothing and reaches one machine. Basic leaves a portal sign-in. Standard adds three ways in, two of which produce no record. Premium adds the record — and does not withdraw the two ways around it.

That is not a criticism of the service. It is the ordinary shape of an access control: the convenient path and the observable path are usually different paths, and the design work is deciding which one you are actually going to permit. Buying Premium is the easy half. Declaring that connections must come through the portal, and then enforcing it somewhere other than a wiki page, is the half that makes the audit answer true.

The one line to take away

Premium gives you session recording; the native client and shareable links give you convenience with no recording at all. Pick the SKU for the trail you need, then decide — in policy, not in hope — which connection methods you are prepared to allow.
