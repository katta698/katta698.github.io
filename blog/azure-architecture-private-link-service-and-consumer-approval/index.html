Azure Architecture Series #92 — Private Link Service and Consumer Approval

Nov 13, 2026 17 min read
✓Verified against current vendor documentation on 13 November 2026. Pricing, limits and API behaviour were checked against the official docs on that date. Cloud services change fast — if you are reading this much later, treat the specifics as a starting point and re-check the linked sources.

Business Challenge

#91 was the consumer's side: a network interface in your subnet that reaches somebody else's service. This is the other end — what you build when the service being reached is yours.

It is your own service, behind a load balancer

“Azure Private Link service is the reference to your own service… Your service that is running behind Azure Standard Load Balancer can be enabled for Private Link access so that consumers to your service can access it privately from their own VNets.”

Which makes it the first thing in this sequence that is a product decision rather than a networking one. A Private Link service is how a software vendor sells into customers' virtual networks without exposing anything publicly, and the two properties that govern it — visibility and autoApproval — are a commercial access model expressed as two arrays of subscription IDs.

They are easy to conflate, and the documentation separates them in one sentence worth memorising:

Visibility is exposure; auto-approval is approval

“Visibility controls the exposure settings whereas auto-approval controls the approval settings for your service… Auto-approval is a subset of the visibility array.”

One decides whether a consumer can request at all. The other decides whether that request lands in your inbox or connects itself. Getting the second one wrong is how a service that was meant to require a conversation starts accepting connections quietly.

Why This Architecture Holds Up

Because auto-approval is a subset, and that is the whole safety property

The two arrays are not independent. “Auto-approval is a subset of the visibility array” — so a subscription cannot be auto-approved without also being visible, and the visibility list is the outer boundary of who can reach you at all.

That ordering is what makes the design safe, and it also means the two settings fail differently. Widen visibility and you get connection requests — noise, but each one still needs a decision. Widen auto-approval and you get connections, with no decision and no notification. The failure is silent in exactly one direction.

The sharpest version of this is the combination the portal makes easy: visibility set to “Anyone with your alias” alongside a populated auto-approval list. That is a defensible configuration — a public service that pre-approves known customers — but the alias is “a globally unique read-only string” shared “offline”, which is to say it is a bearer token with no expiry. Anyone who has ever been sent it can request a connection forever.

And the names reinforce the confusion rather than resolving it. “Role-based access control only” is the most restrictive visibility setting, yet it is the one that “permits” cross-tenant access — because RBAC, not a subscription list, is doing the gating. A reader scanning for “which option keeps this inside my tenant” can pick the wrong one from the label.

Because the provider cannot see who is calling

This is the architectural consequence that shapes everything a provider can build:

Every consumer arrives as one of your own addresses

“Private Link service performs destination side NAT-ing… This NAT ensures that there's no IP conflict between source (consumer side) and destination (service provider) address space. On the destination or service provider side, the NAT IP address displays as source IP for all packets received by your service.”

So a provider's application sees traffic from a handful of its own private addresses, with no way to tell one customer from another. Every per-tenant control that would normally key on source address — rate limiting, IP allow lists, audit logging, abuse attribution — has nothing to key on.

This is the same SNAT trade this series keeps meeting, and it is worth noting how differently it lands each time. #79 found Azure Firewall's SNAT hiding the source the perimeter existed to read — damage. #83 found SNAT mandatory to make return traffic symmetric — a prerequisite. Here it is neither: it is a deliberate isolation guarantee, because without it two customers with overlapping RFC 1918 ranges could not both connect. The translation is the feature.

The documented way back is TCP Proxy v2, and what it carries is more than the address: “In addition to source IP address, proxy protocol header also carries the LinkID of the private endpoint. Combination of source IP address and LinkID can help service providers uniquely identify their consumers.”

That is the mechanism a multi-tenant provider actually needs, and it is worth being precise that it is the LinkID doing the work. The source address alone is a NAT IP shared by everyone; the LinkID is per-private-endpoint and matches linkIdentifier on the connection object, so it joins back to a specific approved consumer. A provider that enables proxy protocol and then reads only the source IP has gained nothing.

Because proxy protocol is all-or-nothing in both directions

Enabling it is not a safe default you can switch on and tune later. Both mismatches fail:

Setting on the Private Link serviceBackend parses the header?Result
EnabledNo“The request will fail”
DisabledYes — expects it“The request will fail”

There is no degraded mode and no negotiation. The two sides must be changed together, which for a service already carrying traffic means a coordinated cutover rather than a toggle.

Two consequences make that cutover wider than it looks. The first reaches the health checks:

“Once proxy protocol setting is enabled, proxy protocol header will also be included in HTTP/TCP health probes from host to the backend virtual machines. Client information isn't contained in the header.”

So the backend must parse a header on probe traffic too — probes that carry no client information, so the parser has to tolerate a header with nothing useful in it. #83 established what happens when a health probe response is wrong: the instance is removed from service while being perfectly healthy. This is a way to cause that across an entire backend pool with one property change.

The second is that the setting is not scoped where its name suggests:

The setting is per-service; the effect is per-load-balancer

“TCP Proxy v2 configuration on a Private Link service activates for all load balancers and their backend VMs. If TCP Proxy v2 is configured on one PLS, configure it on other PLS resources if they are sharing the same load balancer or backend pool, otherwise health probes will fail.”

Up to 8 Private Link services can share one Standard Load Balancer. Enabling proxy protocol on one of them changes the behaviour of all eight, and the failure surfaces on the seven nobody touched. That is a blast radius that does not follow the resource boundary, and the documentation flags it twice — once as a note near the top and once in the limitations list — which is usually how often something has to be reported before it gets written down.

Because the NAT pool is the scaling unit, and it has a floor as well as a ceiling

The NAT addresses are not just for address-conflict avoidance; they are the throughput budget: “service providers can assign up to eight NAT IP addresses per Private Link service. With each NAT IP address, you can assign more ports for your TCP connections and thus scale out.”

Which makes the recommendation at creation time a capacity decision disguised as a subnet-sizing one: “It's recommended to have at least eight NAT IP addresses available in the subnet.” Provision the subnet for one and you cannot scale the service later without moving it.

There is a floor too, and it is unusual in being enforced rather than advised: “you must maintain at least one NAT IP address once configured. You will be restricted from deleting the last remaining NAT IP to ensure that active connections aren't impacted.” Azure refuses the operation rather than letting a provider cut off its own customers — which is the right behaviour and worth knowing before a cleanup script discovers it.

Because the load balancer requirements exclude a common configuration

Standard Load Balancer only, which is expected. The second requirement is not:

“Supported only on Standard Load Balancer where backend pool is configured by NIC. Not supported on Standard Load Balancer where backend pool is configured by IP address.”

Backend pools by IP address are the normal choice for several architectures — backends that are not Azure NICs, or pools managed as addresses rather than resources. A load balancer built that way cannot carry a Private Link service, and the discovery comes at the point of creating the service rather than when the pool was designed.

Three smaller constraints belong with it. “Supports IPv4 traffic only” — the fourth IPv6 gap this series has recorded, after Azure Firewall's DNAT rules, its virtual-hub deployment and the DNS Private Resolver's subnets. “Supports TCP and UDP traffic only.” And an idle timeout that is short enough to matter: 300 seconds, with the explicit instruction that “applications connecting through Private Link Service must use TCP Keepalives lower than that time.” A five-minute idle cut is well inside the range where a connection-pooling client will hold a socket open and assume it works.

Because the alias is permanent and carries your region

The alias is how consumers find you, and two of its properties are fixed at creation. “Prefix is the service name. You can pick your own prefix. After ‘Alias’ is created, you can't change it, so select your prefix appropriately.”

And the suffix is “appended by Azure: region.azure.privatelinkservice”, so the full alias names the region the service lives in. A consumer reading an alias learns where the provider deployed. For a provider that would rather not advertise its regional footprint, that is a disclosure with no setting to turn it off — and combined with immutability, a rename or a region change means a new alias and every consumer reconnecting.

The deletion rule has the same shape: “before you delete the service, ensure that there are no private endpoint connections associated with it. You can reject all connections and delete the service.” The service cannot be removed while anyone is attached, so decommissioning is an explicit act of disconnecting customers rather than a deletion that cascades.

Because reach is wide and the tenant boundary is not a barrier

It is worth being clear how far an approved connection reaches, because it is further than a virtual network: “A single Private Link Service can be accessed from multiple Private Endpoints belonging to different virtual networks, subscriptions and/or Microsoft Entra tenants”, and each of those endpoints is reachable “from the same virtual network and regionally peered virtual networks… globally peered virtual networks and on premises using private VPN or ExpressRoute.”

So one approval can expose the service to a consumer's entire connected estate, including their on-premises networks. The approval is per private endpoint, not per machine or per network — and #89's point about links applies here in mirror image: the unit you approve is coarser than the unit you might want to control.

The provider does keep per-connection control after the fact: “Multiple private endpoints can connect to the same Private Link service and the service provider can control the state for individual private endpoints”, with approve, reject and delete all available. Revocation is per endpoint and immediate in effect, since “only connections that are approved can send traffic”.

One preview changes the shape of all of this and is worth knowing exists: “Private Link Service Direct Connect, which allows you to connect to any privately routable destination IP address” — “connecting to a privately routable destination IP address without requiring a load balancer.” The Standard Load Balancer requirement, which is the first thing this whole design asks for, becomes optional.

Closing Thought

The consumer side of Private Link is a networking feature. The provider side is a product one. What visibility and autoApproval encode is a go-to-market model — private to my own tenants, restricted to named customers, or open to anyone holding a string — and the technical settings are thin enough that the commercial decision is the whole of it.

The property to be careful with is the one whose failure is quiet. Visibility that is too broad produces requests, and a request is a prompt to think. Auto-approval that is too broad produces connections, and a connection asks nothing of anyone. Those two lists sit next to each other in the same resource, with the second defined as a subset of the first, and only one of them has a human in the loop by construction.

The thing I would design around from the start, though, is that the provider never sees who is calling. Destination-side NAT is not a limitation to work around — it is what lets two customers with the same private address range both connect, which is the entire reason this works as a multi-tenant product. But it means every per-customer control a SaaS normally builds on source address has nothing underneath it. The LinkID in the proxy protocol header is the only durable identity on the wire, and getting it requires a protocol change that must land on both sides at once and that reaches further than the resource it is set on. That is worth deciding before the first customer connects, not after the hundredth.
