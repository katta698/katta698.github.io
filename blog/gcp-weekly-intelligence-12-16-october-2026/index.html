The week in one paragraph

236 notes across 54 products and five days, up from 157 — and unusually, the volume is not the story. Four separate things shipped as coordinated multi-product launches rather than as single notes, which makes the week read very differently from its inventory. Service rate limiting appeared in Cloud Armor, Secure Web Proxy and regional internal Application Load Balancers on the same day. Private Service Connect became the default private IP option for new instances across all three Cloud SQL engines. Google-managed certificate lifetimes began halving, announced twice. Spend caps went GA in Cloud Billing and Cloud Run together. Meanwhile the security bulletins feed produced two items after producing none for three weeks, and the pair of them make a useful point about reading severity.

Two bulletins, and why severity does not tell you whether to act

The two bulletins this week are rated Critical and High, and the Critical one is the one you can ignore. That inversion is worth sitting with, because the instinct to triage by severity gets it exactly backwards here.

GCP-2026-068, published 14 October and rated Critical, is an Incorrect Authorization vulnerability in the AuthConfig validation and integration execution runtime in Application Integration versions prior to August 27, 2026. The impact is as bad as the rating suggests: an authenticated user could escalate privileges and impersonate a service account in the Google Cloud project. And the instruction is one line — no customer action is required. This vulnerability was patched on August 27, 2026. It carries CVE-2026-85298.

GCP-2026-067, published 12 October and rated High, is a Denial-of-Service (DoS) vulnerability was discovered in Envoy Proxy when an HTTP filter — specifically one that mutates the :path header after route selection on a route configured with prefix_rewrite. This one does not say no action is required. It says for instructions and more details, see the Cloud Service Mesh security bulletin, and it is tracked upstream as envoyproxy/envoy#47841 rather than under a CVE.

The reading that matters

Severity scores the vulnerability, not your workload. The Critical was fixed in the managed service seven weeks before it was disclosed, so by the time you read it the exposure is historical. The High is in a data-plane proxy you run, with conditions you may or may not meet, and it points you at instructions — which means somebody has to go and check whether their ext_proc filter does what the bulletin describes. Triage on what is being asked of you, which the bulletin states plainly, before triaging on the colour of the label.

One factual pattern alongside it, since this series tracks the bulletins feed week to week: GCP-2026-068 is the third consecutive Application Integration bulletin, after GCP-2026-066 and GCP-2026-065 on 28 September. All three describe an authenticated user reaching further than they should — privilege escalation here, a confused deputy and an untrusted-deserialisation issue in the previous pair. That is an observation about where disclosures are landing, not a judgement about the product.

Service rate limiting arrives in three products at once

The week's most substantial new capability was published three times on 14 October, once per surface it applies to. Service rate limiting policies are now available in Preview for regional internal Application Load Balancers and Secure Web Proxies, and the purpose is stated more precisely than "rate limiting" usually is: service rate limiting policies let you maintain service availability among trusted clients that might consume an inordinate amount of resources.

That phrase is the whole design. This is not abuse prevention — Cloud Armor already does that for untrusted traffic. It is protection against your own well-behaved clients, the internal consumer whose retry loop or batch job is indistinguishable from a healthy caller except in volume. Hence the surfaces it landed on: Secure Web Proxy supports service rate limiting policies, applying to Secure Web Proxy gateways whether they use an authorization policy or a gateway security policy, and separately Cloud Armor supports service rate limiting, also in Preview.

Worth noting what the internal load balancer case gives you that the previous four architecture posts could not. Those posts established that a subnet boundary carries no policy, that firewall rules are enforced at the VM, and that there is no choke point between subnets to inspect. A rate limiting policy on a regional internal Application Load Balancer is a choke point — a place in the path where a quantitative policy about a trusted caller can be enforced. It is the first thing in this block of the series that behaves like the mid-network control the model otherwise lacks.

Private Service Connect becomes the Cloud SQL default

On 13 October the same sentence was published under Cloud SQL for MySQL, Cloud SQL for PostgreSQL and Cloud SQL for SQL Server: private Service Connect is now the default private IP connectivity option when you create a Cloud SQL for MySQL instance in a new Google Cloud project, and likewise for a Cloud SQL for PostgreSQL instance and a Cloud SQL for SQL Server instance. The stated advantages are reach and automation — it lets you connect from multiple VPC networks across different groups, projects or organizations, and it supports automatic endpoint and DNS record provisioning.

Two qualifiers deserve emphasis because they bound the change tightly. It applies to new instances in new projects, so nothing existing moves. And it is a default rather than a requirement — when you configure private IP for an instance you can still choose private services access instead.

Why a changed default is worth a paragraph

This week's architecture post was about an operation whose risk lived entirely in what it left behind, and the post before it was about a default chosen on your behalf by project creation. A connectivity default that changes for new projects only is the same shape: nothing breaks, nothing migrates, and two projects created three weeks apart now differ in how the database is reached. If you have Terraform that asserts private services access, or a runbook describing how to reach the instance, the divergence shows up the first time somebody follows it in a new project.

Certificates halve to 45 days, and you do nothing

Announced twice on 14 October, under Certificate Manager and again under Cloud Load Balancing: Google-managed public SSL certificates signed by Google Public CA (pki.goog) are gradually transitioning from a 90-day validity period to a 45-day validity period to improve security. Half the lifetime means twice the rotations, and Google-managed public certificates now rotate more frequently as a result; Google frames the benefit as the obvious one, that this proactive rotation enhances the overall security posture of load balancers.

The important half of the note is the part that is easy to skip past, and it is the reason this is not an action item: transition requires no manual intervention or configuration changes as Google Cloud automatically manages issuance and renewal for both Certificate Manager and Compute Engine SSL certificates. Both certificate surfaces, issuance and renewal, handled. For almost everybody this is a change you will never observe.

The exception is anything of yours that encoded 90 days as a fact rather than reading it from the certificate — a monitoring threshold that alerts when expiry is more than so many days out, a compliance export that records certificate lifetime, a dashboard panel with a hardcoded renewal window. Those do not break; they quietly start describing something that is no longer true, which is the same failure mode as every other item in this week's roundup.

Networking, platform and the rest

Cloud DNS gained outbound endpoints. Outbound Endpoints for Cloud DNS is available in Preview, and the mechanism is specific: attach Outbound Endpoints to forwarding zones or server policies to enable direct DNS query forwarding from VPC networks to external and on-premises DNS resolvers using private IP addresses. For hybrid resolution this is the piece that previously needed an inbound forwarding relay on the other side.

VPC Service Controls learned about GKE workload identity. Support for using Workload Identity Federation for GKE in ingress and egress rules to allow access to resources protected by a service perimeter is available in Preview, and the granularity is per service account, per namespace — all GKE Pods in a Kubernetes namespace — or per cluster. A perimeter rule can now name a Kubernetes identity rather than the project around it. The accompanying blog post, Modernizing perimeter security: Scalable perimeters with VPC Service Controls, landed on 15 October.

Load balancing and networking fixes. Regular expression matchers in host and route rules in URL maps are now generally available (GA). And a billing correction worth checking if it affected you: the technical issue causing incorrect billing for producer VPC spokes has been fixed in Network Connectivity Center.

Compute. Generally available: the network-optimized C4N machine types with 375 GiB to 12,000 GiB of attached Titanium SSD are now generally available. Hyperdisk volumes in multi-writer mode can now be grown while attached to multiple instances, and regional read-only views of global project and image resources went GA.

Cost controls, in two products. Spend cap budgets are now generally available for a limited set of services, and alongside it support for Budget spend caps to pause your Cloud Run workloads is in General Availability (GA). A budget that pauses workloads rather than emailing somebody is a materially different control from a budget alert.

One deprecation to note, in two APIs. The emotion label response in the Cloud Vision API is deprecated and face detection will return UNKNOWN for all emotion-related labels; the Video Intelligence API published the equivalent note the same week. Anything consuming emotion labels now receives UNKNOWN rather than an error, so the failure is silent by design.

What I would act on

  1. Check whether your Envoy configuration matches GCP-2026-067, and follow the Cloud Service Mesh bulletin. This is the one bulletin of the two that asks something of you. The trigger is specific — an HTTP filter that mutates the :path header after route selection on a route with prefix_rewrite — so it is answerable by inspection rather than guesswork.
  2. Find anything that hardcodes a 90-day certificate lifetime. Monitoring thresholds, compliance exports, dashboards. The rotation itself needs no intervention; the assertions you wrote about it do.
  3. Decide your Cloud SQL private connectivity standard before the next new project. The default is now Private Service Connect for new instances in new projects, private services access is still selectable, and the cheapest moment to make that an explicit choice is before two projects diverge by accident.
  4. If you run internal services with trusted but noisy clients, try service rate limiting in Preview. It is the first control in this area aimed at well-behaved callers consuming too much, rather than at abuse, and it sits in the request path where nothing else in the VPC model does.
  5. Audit anything reading emotion labels from Cloud Vision or Video Intelligence. It will not error. It will return UNKNOWN, which a downstream consumer may happily record as a result.
