The week in one paragraph

Two hundred and eighty-five notes across 66 products and five working days, and nine security bulletins — 082 through 090, which is the heaviest security week this series has covered. The volume is unremarkable; the bulletins are not. One CVE pair in NGINX was filed twice, in two bulletins, at two completely different scopes, and reading only one of them gives you the wrong picture of your exposure. A Linux kernel TCP flaw can panic a GKE node or a cluster control plane, and Google says plainly that traffic from inside your own VPC network is enough to trigger it. A GKE encryption setting turned out to encrypt Secrets when it reported encrypting everything. Underneath, Container-Optimized OS was 91 of the 285 notes across 8 releases, and the networking items — an Azure interconnect preview, namespace-level NAT for GKE, and deny-by-default authorization policies reaching GA — all land directly on ground this architecture series has just covered.

The NGINX pair, filed twice at opposite scopes

GCP-2026-087 and GCP-2026-089 cover the same two CVEs and are not the same bulletin. Reading either alone leaves you with a wrong answer, which is why this is the week's headline rather than its footnote.

The narrow one came first. GCP-2026-087 Published: 2026-11-19 says two vulnerabilities in the nginx HTTP/2 module, CVE-2026-123633 and CVE-2026-123007, can let a remote, unauthenticated attacker run code on an nginx server that accepts HTTP/2 connections. Its scope is one product: the Router in Apigee Edge for Private Cloud 4.54.00 and 4.53.01 uses an nginx version in the affected range. And its verdict is reassuring, with a reason attached — routers are not affected in the default and supported configuration, because HTTP/2 is not supported on Router virtual hosts.

The next day the broad one landed. GCP-2026-089 Published: 2026-11-20, and it reframes the whole thing: on November 18, 2026, F5 disclosed HTTP/2 vulnerabilities CVE-2026-123633 and CVE-2026-123007 in NGINX Open Source (1.19.7-1.31.8 for CVE-2026-123633; 1.9.5-1.31.8 for CVE-2026-123007) and NGINX Plus, alongside eight additional NGINX CVEs in F5's master advisory. The impact is both ends of the severity range: under specific configuration and traffic conditions, an unauthenticated remote attacker can crash an NGINX worker process (DoS) or potentially achieve remote code execution (RCE).

Where the line falls

The division is clean and worth quoting exactly, because "are we affected?" has a different answer for each half of a typical estate. Google Cloud's core load balancing and managed infrastructure (including Google Front End, Cloud Load Balancing, GKE control plane, Cloud Run, Cloud Functions, and App Engine) are not affected. Then: this bulletin provides guidance for customers operating self-managed NGINX deployments on Google Cloud.

So the managed side is closed — Google is patching any isolated Google-managed components internally, with zero customer impact and no customer action required — and everything you run yourself is open. GKE Ingress controllers, NGINX on Compute Engine VMs, and NGINX-based Marketplace images are all named as yours.

One line in that bulletin is unusual enough to be the detail I would remember from this week: Google has also temporarily delisted affected Google-maintained Click-to-Deploy NGINX listings on Cloud Marketplace while patched images are being prepared. A vendor pulling its own catalogue entries mid-incident is a strong signal about the images already deployed from them, and it is the kind of action that leaves no trace in your project — a VM built from one of those listings last month is still running the vulnerable build, and nothing in the console will say so.

The remedy is a version number: upgrade NGINX Open Source to 1.31.9 (mainline) or 1.30.7 (stable), with NGINX Plus on its own fixed releases.

A kernel TCP panic your own VPC can trigger

GCP-2026-088 Published: 2026-11-19 Updated: 2026-11-20. A denial-of-service vulnerability (CVE-2026-99288) was discovered in the Linux kernel TCP implementation.

The blast radius is scoped honestly in both directions. What it cannot do: the flaw can cause a kernel panic (denial of service) on the affected virtual machine; it does not allow privilege escalation or container breakout to code execution on the host. What it can: a remote attacker can trigger it by sending specially crafted TCP packets to a reachable TCP listener on a node, Pod, or the cluster control plane's IP-based endpoint.

And then the sentence that changes the risk assessment for anyone relying on private networking as the control: internal traffic within the same VPC can also trigger this vulnerability. Everything posts #90 through #96 built — Private Google Access, VIPs, Private Service Connect, private services access — keeps traffic off the public internet. None of it helps here, because the attacker does not need to be on the public internet. A compromised workload on an authorized network is enough, and the target can be the control plane.

Two exclusions are worth checking your fleet against: pods running in GKE Sandbox (gVisor) and Windows Server node pools are not affected. And the patch status was still incomplete when the week closed — the 20 November update added fixes for minor versions 1.32 and 1.33, while patches for GKE 1.37 on Container-Optimized OS and Ubuntu node images are still in progress. If your clusters are on the newest minor version, this one is not finished.

The GKE setting that encrypted less than it reported

Filed as an Issue rather than a bulletin, and it belongs with the security items because of what it quietly did not do. In GKE versions 1.35, 1.36, and 1.37, enabling application-layer secrets encryption on a new or existing cluster whose control plane stores cluster state in Spanner encrypts only Kubernetes Secrets (ENCRYPTED) instead of all Kubernetes API objects (ALL_OBJECTS_ENCRYPTION_ENABLED).

So the feature was enabled, the cluster reported a state, and the state was narrower than the one intended. Two mitigating facts: clusters that already have encryption of all Kubernetes API objects enabled (ALL_OBJECTS_ENCRYPTION_ENABLED) continue to encrypt all objects, and a fix to restore encryption of all Kubernetes API objects for newly configured clusters is in progress. Existing full-encryption clusters were not downgraded; newly configured ones got less than they asked for.

There is an operational tail that outlives the bug, and it is the part to write down: clusters where application-layer secrets encryption is in the ENCRYPTED state encrypt only Secrets and require manual Secret re-encryption after a Cloud KMS key rotation. A key rotation that you expect to re-protect everything will leave work behind on these clusters, and that is true until they are moved to the other state.

Worth checking rather than assuming, because the clusters in question are identified by an implementation detail — whether the control plane stores state in Spanner — that is not something most teams track.

Networking: Azure interconnect, namespace-level NAT, deny by default

Three networking items this week, and each one lands on a post in this architecture series — one behind it, one ahead of it, one beside it.

Partner Cross-Cloud Interconnect reaches Azure

Partner Cross-Cloud Interconnect for Microsoft Azure is available in public preview. Post #89 covered Cross-Cloud Interconnect as the dedicated product; the Partner variant is the lower-bandwidth, service-provider-fronted path, and Azure joining the supported list makes a Google–Azure private link something you can procure through a partner rather than build end to end. Public preview, so not for production commitments yet, but it changes the shape of a multicloud design conversation.

GKE Granular NAT, one post early

GKE Granular NAT is now available in Preview for Autopilot and Standard clusters running GKE version 1.37.1-gke.2611000 or later with GKE Dataplane V2 enabled. The point of it is scope: instead of applying a single NAT policy to an entire cluster, you can route egress traffic from specific namespaces through dedicated external IP addresses for Public NAT or dedicated subnet IP address ranges for Private NAT, without managing custom proxy instances.

That is a direct answer to a real problem — a partner who will only allowlist a specific source address, in a cluster that NATs everything through one pool — and the usual workaround has been a proxy nobody wants to own. It arrives the week before this series reaches Cloud NAT, which is convenient timing for me and useful context for anyone planning that work: per-namespace egress addresses are now a platform feature rather than a design exercise.

Deny by default for Application Load Balancers

The DENY_BY_DEFAULT action for authorization policies is generally available (GA) for regional external Application Load Balancers, regional internal Application Load Balancers, and cross-region internal Application Load Balancers. The semantics are what the name promises: attaching a DENY_BY_DEFAULT authorization policy to a load balancer's forwarding rule establishes a deny-by-default security baseline that blocks all requests unless they are explicitly permitted by a separate ALLOW or CUSTOM authorization policy.

Note the pairing requirement. A DENY_BY_DEFAULT policy on its own blocks everything, so this is a two-policy pattern — which makes it a change to deploy carefully and in the right order, since getting it half-applied takes the service down rather than leaving it open.

And a default that is now arriving on its own

Cloud Load Balancing has entered Phase 2 of the rollout for TLS post-quantum key exchange support across Application Load Balancers and external proxy Network Load Balancers. Phase 2 is the one that matters, because the default flipped: in Phase 2 (October 2026 through October 2027), TLS post-quantum key exchange is enabled by default. You can still defer with an SSL policy, and the deadline for that is published — Phase 3 (After October 2027): Post-quantum key exchange will be enabled always, and deferral options will no longer be effective.

If an intermediate device or an old client library cannot negotiate it, the symptom appears at the load balancer and the opt-out window is finite. Worth testing now rather than in late 2027.

What I would act on

Four things, in the order I would do them.

1. Inventory self-managed NGINX, including what came from Marketplace. GCP-2026-089 draws the line at "managed by Google" versus "managed by you", and the delisted Click-to-Deploy listings mean some of your instances were built from images Google itself has withdrawn. Upgrade to 1.31.9 or 1.30.7. This is the only item this week with a credible remote code execution path.

2. Check GKE minor versions against GCP-2026-088. Clusters on 1.32 and 1.33 have patches as of 20 November. Clusters on 1.37 do not yet. And because internal VPC traffic can trigger it, do not discount this on the grounds that the nodes are private — that is precisely the assumption the bulletin removes.

3. Verify what your clusters are actually encrypting. If any cluster on 1.35, 1.36 or 1.37 had application-layer secrets encryption enabled recently, confirm whether it is in the ENCRYPTED or ALL_OBJECTS_ENCRYPTION_ENABLED state. The second thing to note is the Cloud KMS rotation caveat, which is an ongoing operational difference, not a one-off.

4. Test post-quantum TLS negotiation against your load balancers. The default is already on, the deferral is already available, and Phase 3 already has a date. A test this quarter costs an hour; discovering an incompatible middlebox after October 2027 costs an outage with no opt-out left.

The PHP session handler bulletin, GCP-2026-090, is a fifth item for anyone running PHP. The immediate mitigation is a one-line configuration change — session.upload_progress.enabled = 0 — recommended on the basis that if your application does not require tracking upload progress, disabling this feature in php.ini mitigates the primary attack path. The structural fix is the one to plan: where feasible, switch PHP session storage away from local filesystem handlers to Redis, Memcache or a database. And check your runtime version against the list, because two entries have no fix at all — PHP 8.1, PHP 7.2 (end of life, no fix available).

The two VMware bulletins, GCP-2026-085 Published: 2026-11-19 and GCP-2026-086 Published: 2026-11-19, matter only if you run VMware Engine. The first is vCenter — a vulnerability was identified in VMware vCenter and VMware Cloud Foundation (VCF), with there are no known workarounds for this reported vulnerability. The second is a vulnerability was identified in VMware Aria Operations and VMware Cloud Foundation (VCF). Both point at Broadcom for remediation.
