The week in one paragraph

Three hundred and twenty-two notes across Monday to Friday, five security bulletins, and for once the bulletins are the story rather than the footnote. Two of the five describe the same event from different angles: the private keys of eight subordinate certificate authorities were compromised, which makes this a trust-store problem rather than a Google Cloud problem, and the remediation is a list of package versions in your own dependency file. A third describes a Linux kernel flaw that is a container escape, affecting GKE Standard and Autopilot alike. The only Critical of the week is narrower than it reads and touches one VMware product that is explicitly not the Google Cloud one. Underneath all that, the volume was ordinary: Container-Optimized OS accounted for 131 of the 322 notes on its usual run of kernel and CVE rebuilds, and Looker for another 37.

A CA lost its private keys, and the fix is not in Google's SDK

Two bulletins, GCP-2026-075 on Monday and GCP-2026-077 on Tuesday, cover one underlying event. The first gives the timeline and the scope: on Saturday, October 17, 2026, Google received a report from a security researcher regarding the compromise of private keys associated with eight eMudhra subordinate Certification Authority (CA) certificates, including those cross-signed by AAA Certificate Services. Consequently these CA certificates are no longer trusted and are being revoked.

Two sentences in that bulletin are there to stop a particular misreading, and they are worth quoting exactly because they will be the first thing anyone asks: Google Cloud infrastructure has not been breached. And security telemetry shows no evidence of exploitation against Google Cloud workloads. Nothing of Google's was broken into. What happened is that certificates your code may still trust can now be forged by somebody else.

The consequence is spelled out on the Apigee side in GCP-2026-077: outbound TLS connections trusting affected roots-specifically emSign ECC Root CA - G3 -are vulnerable to Man-in-the-Middle (MITM) interception, because an attacker possessing compromised intermediate keys can issue fraudulent TLS certificates for arbitrary domain names. For Apigee specifically, outbound HTTPS connections made from Apigee runtimes (such as TargetEndpoints, TargetServers, ServiceCallouts, and outbound JWKS policy lookups) using default or unmanaged system trust stores may accept forged certificates. Note which direction that is. This is not about certificates you serve; it is about certificates you accept when your own code calls out.

The exposure test is a single question: does your TLS trust store still accept the affected roots? The bulletin puts it as applications built with the Google Cloud SDK Libraries are affected if their TLS trust store still accepts emSign ECC Root CA - G3 , emSign Root TLS CA - G3 , or AAA Certificate Services.

Why patching the operating system is not enough

This is the part worth understanding properly, because it determines whether your remediation actually works. Google's own libraries are mostly not where the trust store lives: the Google Cloud SDK Libraries themselves don't bundle CA certificates, with one exception: Java's com.google.api-client: google-api-client before 2.9.2. Otherwise the trust store comes from a transport dependency (including the Google-maintained gRPC packages), the language runtime, or the operating system — so the fix is an update to those rather than to the Google Cloud SDK Libraries.

Which means the instinctive response, rebuild the base image and move on, fixes only one of three possible sources. For Python the bulletin names all three, and the third is the one that defeats an OS-level fix:

  • certifi earlier than 2026.10.19 (REST transports)
  • httplib2 earlier than 0.32.1, used by google-api-python-client and google-auth-httplib2 — and its bundled trust store is used when certifi is not installed
  • grpcio earlier than 1.84.1 (gRPC transports); bundled root store, does not read the operating system trust store

Read that last one twice. A gRPC client carries its own root store and ignores the operating system's, so a fully patched host with an old grpcio wheel is still exposed, and every signal you would normally trust — the base image is current, the OS packages are current — says you are fine. The remediations are correspondingly specific: upgrade certifi to 2026.10.19 or later, upgrade httplib2 to 0.32.1 or later, upgrade grpcio to 1.84.1 or later. For the other ecosystems there is a shortcut, since in Java, Ruby, and PHP, upgrading the Google client libraries also pulls the fix in.

And the step that is easy to skip when the fix is a version bump in a lock file: then rebuild and redeploy your container images. A patched requirements file in the repository protects nothing that is still running.

A kernel flaw that is a container escape

GCP-2026-078, published Wednesday, is rated Medium and reads considerably worse than that. A vulnerability (CVE-2026-98432) was discovered in the Linux kernel IPv4 TCP stack, and the flaw can cause a kernel panic or a container escape (root code execution on the node).

There are two ways in, and the first has no precondition worth the name: an unprivileged process in a container can trigger it locally, without special capabilities such as CAP_NET_RAW. No elevated capability, no privileged pod, nothing a Pod Security admission policy would normally catch. If you run other people's code, or your own code that processes other people's input, that is your threat model.

The second way in is remote: a network attacker can also trigger it by sending TCP packets with IPv4 options to a listener on the node or on the cluster control plane. Here there is a precondition, and it is the familiar one — the network attack requires access to a TCP listener on your nodes, Pods, or the control plane's IP-based endpoint. Which produces the sentence that decides whether this is urgent or merely important for you: clusters that restrict this access to trusted sources, for example with firewall rules and control plane authorized networks, are not exposed to network attacks.

Note what that does and does not buy. Authorized networks and firewall rules close the remote path. They do nothing about the local path, and the local path needs no capabilities. So the control that usually counts as sufficient here only halves the problem, and GKE Standard clusters and GKE Autopilot clusters are impacted — Autopilot's managed node layer is not an exemption, it is the reason you wait for the patched versions rather than patching nodes yourself.

The week's only Critical is narrower than it looks

GCP-2026-079 on Thursday is the single Critical, and the scope line matters more than the rating. Per advisory VMSA-2026-0008, Broadcom has identified an out-of-bounds write remote code execution vulnerability in the SDDC Manager Node.js Brotli decoder. But: this impacts only VMware solution on Google Cloud running VMware Cloud Foundation 9.1.x and does not impact Google Cloud VMware Engine. Two similarly named products, one affected. Remediation is not Google's to ship — apply the Broadcom-recommended workarounds outlined in the VMSA-2026-0008 advisory. CVE-2026-111497.

The fifth bulletin, GCP-2026-076 on Monday, is brief: a security vulnerability was discovered in Istio, tracked as CVE-2026-111943 and rated Medium, with details in the Cloud Service Mesh bulletin. If you run Cloud Service Mesh it is a version bump; if you do not, it is nothing.

Networking, data and governance

The non-security week had one item that matters to anyone who has been putting IPv6 off. On Cloud Load Balancing, frontend configuration for load balancing incoming IPv6 traffic is now generally available (GA) for a set of load balancers including the regional external Application Load Balancer. Read against this series' current run through hybrid networking, that is the second IPv6 signal in two days: #85 noted that HA VPN supports dual stack and IPv6-only while Classic VPN supports neither. The dual-stack path is steadily becoming the default-supported one, and the products that do not support it are the older generation in each pair.

One governance change is worth diarising even though it is phrased gently. In Security Command Center, Data Security Posture Management (DSPM) is no longer available to new organizations. Existing organizations with it enabled retain access; new ones cannot turn it on. If DSPM is in a reference architecture or a landing-zone blueprint you hand to new organizations, that blueprint now has a hole in it, and the failure will surface as a feature that simply cannot be enabled rather than as an error anyone has explained.

For VPC Service Controls there is a quiet addition: general availability support for the following integration: Service Management. Each of those integrations is one more API that can be brought inside a perimeter, and the list is the real measure of whether a perimeter is worth building for a given estate.

On the data side the notable one is a pricing-tier change rather than a feature: you can now use BigQuery Graph and run Graph Query Language (GQL) queries when you use on-demand pricing. Graph queries were previously the kind of thing you needed a reservation to try, and on-demand availability is what turns an evaluation into an afternoon rather than a procurement exercise.

Four more items sit in the diary rather than the backlog, all of them dated or already in force: the BigQuery Data Transfer Service Shopify connector drops several fields from 31 January 2027; Gemini Notebook Enterprise is changing its web address, so saved links will need revisiting; Apigee Edge Microgateway 3.3.12 removed support for Node.js 20 and now supports only 22, 24 and 26; and Google SecOps deprecated the ListCaseEvents API endpoint effective 2 November 2026, which is to say already.

Everything else was volume. Container-Optimized OS shipped 131 notes across its LTS refresh releases, almost all of them kernel and package CVE fixes rolled into new milestones; the rolled-up section of the inventory below lists every distinct CVE identifier rather than collapsing the count. Looker contributed 37, and the agent platforms — Agent Registry reaching GA for standalone skills, with security scanning and governance alongside it — contributed most of the rest.

What I would act on

Four things, in the order I would do them.

One: inventory your transport dependencies, not your base images. The CA compromise is remediated in certifi, httplib2 and grpcio at specific versions, and the gRPC case ignores the operating system trust store entirely. So the question to ask of every deployed service is not "is the image current" but "which of these three is in the lock file, and at what version". Then rebuild and redeploy, because a corrected lock file protects nothing still in flight. If you run Java, check google-api-client against 2.9.2 — it is the one Google library that does bundle certificates.

Two: check whether your clusters restrict access to node and control-plane listeners. That single control is what separates "exposed to a remote container escape" from "exposed only to a local one". Authorized networks and firewall rules on the control plane endpoint are the named mitigations, and they are worth confirming rather than assuming — they tend to be set once, early, by somebody who has since left the team.

Three: accept that the local path needs a patched version, not a policy. An unprivileged process with no special capabilities is enough, which means admission policy does not help and neither does dropping capabilities. Track the patched GKE versions and take them on both Standard and Autopilot.

Four: if DSPM appears anywhere in a landing-zone design, note that new organizations can no longer enable it. Better to discover that while reading a release note than while provisioning a new organization against a blueprint that assumes it.
