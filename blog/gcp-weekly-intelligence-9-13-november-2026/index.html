The week in one paragraph

Three hundred and twenty-one notes across Monday to Friday and only two security bulletins, which makes this the quietest security week in a while and the most interesting deprecation week. The bulletin that matters is a processor-level side channel on fifth-generation AMD EPYC hardware, and its structure is worth reading carefully because Google has fixed one boundary and explicitly left another to you. The deprecation that matters is Policy Controller, which now carries four dates and a hard coupling to GKE version upgrades — meaning a product being retired can block your clusters from moving forward. Underneath, the volume was ordinary: Container-Optimized OS accounted for 123 of the 321 notes, GKE for 19, and the agent platforms for most of the rest.

The AMD bulletin, and the half that is yours

GCP-2026-081, published Monday, is the week's substantive security item. AMD has disclosed three vulnerabilities that affect 5th generation AMD EPYC processors (code-named Turin) — specifically CVE-2024-36350 and CVE-2024-36357, which AMD previously disclosed for earlier EPYC processors, and a new vulnerability, CVE-2026-0004.

The mechanism is a classic microarchitectural leak: under certain conditions, an attacker could infer data from the store queue or the L1 data cache, potentially leaking sensitive information across privilege boundaries.

Check your fleet against the list rather than guessing, because it is specific: affected Compute Engine machine series: C4D, N4D, H4D, Z4D, and G4, including C4D and Z4D bare metal instances. The letter D is doing a lot of work in that list.

Two boundaries, one of them already handled

This is the part to read twice, because it determines whether you have work to do. Google has applied mitigations that protect against attacks between VMs and between VMs and the host. So the multi-tenancy boundary — the one most people worry about first with a CPU vulnerability — is closed, and closed without you doing anything.

The other boundary is not: to protect against attacks inside a VM, such as between processes, you need to update your guest operating system. If a VM of yours runs more than one trust level — multiple tenants' code, untrusted user submissions, a CI runner executing arbitrary build steps — that is the boundary this leaks across, and it is yours to close.

The remediation has two steps and the second is the one that will be skipped. First, update your guest operating system when your OS vendor releases fixes. Then the enabling condition, which is on Google's side: starting November 10th, Google will update the CPU information that VMs report so that patched guest kernels can turn on their mitigations. A patched kernel does nothing until it can see that the CPU supports the mitigation.

The sentence that will cost someone a day

After the update reaches your VM, stop and start the VM. Rebooting the guest OS isn't enough.

A reboot from inside the guest does not re-read the CPU information the hypervisor presents; only a stop and start does. So the obvious verification — patch, reboot, check the kernel reports the mitigation active — will show the mitigation off, and the natural conclusion is that the patch failed. It did not. The VM needs a full stop and start, which on a production fleet is a scheduling problem rather than a technical one, and worth planning as such.

Two cases get their own instructions. For your own stacks: if you run your own OS or hypervisor on a bare metal instance, apply your vendor's fixes when they're available, with the same stop-and-start requirement for nested hypervisors. And for managed Kubernetes, updated GKE node images for Turin-based bare metal instances will be made available — so the GKE path is an image upgrade rather than anything hand-rolled.

Policy Controller is deprecated, and it blocks GKE upgrades

The week's most consequential non-security item, because it has dates and a dependency. Policy Controller is deprecated as of November 12, 2026, and reaches end of support on December 31, 2027.

Before that, two earlier gates. The first closes new adoption: starting January 31, 2027, you can't enable Policy Controller in fleet host projects that don't already have Policy Controller enabled. So if it is in a landing-zone blueprint or a platform standard, that standard has a deadline on it — after January it cannot be applied to anything new.

The second is the one that turns a deprecation into an operational constraint: Google Kubernetes Engine (GKE) blocks upgrades to version 1.39 and later for clusters that have Policy Controller installed. And correspondingly, clusters that run GKE version 1.39 and later don't support Policy Controller.

Read that as a scheduling conflict, not a notice

A deprecated governance product now gates your Kubernetes version upgrades. That is an unusual shape: normally a deprecation lets you keep running the old thing while you migrate, and the cost of delay is only support. Here the cost of delay is that your clusters stop moving — and cluster version upgrades are not optional indefinitely, because GKE versions themselves age out.

So the migration off Policy Controller is not a 2027 task with a December deadline. It is a task constrained by whenever you next need GKE 1.39, which for most estates is sooner. Worth finding out this week which of your clusters have it installed, because that list is the real project plan.

Istio, Looker and the rest

The other bulletin is brief but was revised mid-week, which is itself worth noting — GCP-2026-080 Published: 2026-11-09 Updated: 2026-11-12. The content: security vulnerabilities were discovered in Istio ( ISTIO-SECURITY-2026-009 ), rated High, tracked as CVE-2026-31836 alongside five GitHub advisories. If you run Cloud Service Mesh this is a version bump, and the Thursday revision is a reason to re-read it rather than relying on Monday's copy.

On Looker, a security default flipped: two-factor authentication (2FA) is now enabled by default for all new and existing Looker (original) instances that use email and password authentication and that didn't opt out during the advance opt-out window. Note the scope — existing instances, not just new ones, and only those using email and password authentication. The escape hatch remains: administrators retain full control to manage or disable 2FA by using the Admin > Authentication > Two-Factor panel. If you have service-style logins on email and password, this is the week they started needing a second factor.

One more that will surprise a build pipeline: in Managed Service for Apache Airflow, upgraded the pip package from version 23.2.1 to version 26.2.2. That is not an increment, it is three years of pip in one step, and pip's resolver behaviour and deprecation warnings have changed considerably across that span. Any DAG that installs dependencies at runtime should be tested against it rather than assumed compatible.

Elsewhere the week was volume and AI. Container-Optimized OS shipped 123 notes on its usual run of kernel and package rebuilds; the inventory below rolls those up and lists every distinct CVE identifier rather than collapsing the count. GKE contributed 19, including an experiment with ClusterNetworkPolicy. Two blog items are worth a click for anyone who followed the last fortnight of this series: one on Cross-Cloud Interconnect with a partner carrier, which is #88 and #89's material in practice, and one on what is new in Organization Policy, which is where the governance thread from the #74 to #82 run continues.

What I would act on

Three things, in order.

One: list your C4D, N4D, H4D, Z4D and G4 instances, then ask which of them run more than one trust level. Google has closed the VM-to-VM and VM-to-host boundaries for you. The in-VM boundary is the one you own, and it only matters where a single VM runs code of differing trust — CI runners, multi-tenant workers, anything executing user-supplied code. That intersection is usually much smaller than the machine list, and it is the actual work.

Two: when you patch those guests, plan a stop and start rather than a reboot. The bulletin is explicit that rebooting the guest OS is not enough, so the rollout is a maintenance window with instance restarts, not a package update. Budget for that before promising a date.

Three: find out which clusters have Policy Controller installed. It is deprecated, it cannot be newly enabled after January 2027, and it blocks GKE upgrades to 1.39 and later. The deadline that will actually bind is your next required cluster upgrade, not the December 2027 end of support.
