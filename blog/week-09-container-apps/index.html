Week 9 — Nothing Runs Until Someone Asks

Eight weeks of building the place things run, and nothing was actually running. This week deploys a real workload that serves traffic, costs nothing while idle, and sends one unlucky user the bill for waking it up.

Lab Overview

An internal tool gets used nine times a day, all of them between 9am and 5pm, all of them by the same four people. On a virtual machine it costs the same at 3am as it does at noon. Most internal software looks like this, and most of it is billed as though it were busy.

The alternative is to run nothing when nobody is asking. That is free, and it is not free — somebody has to wait while a container starts. This week deploys that trade and measures both ends of it.

DifficultyIntermediate — assumes containers and Terraform; the scaling behaviour is what the week is about
Time to completeAbout an hour. The scale-to-zero test cannot be hurried: it waits for the idle timer, which took 602 seconds here

Cloud Services and Concepts

Azure Container Apps runs containers without you running the servers underneath them. You hand Azure an image and a few numbers; it decides how many copies to run and when to stop them. Four ideas carry the rest of this post:

  • A replica is one running copy of your container. You are billed per second for the CPU and memory each copy is allocated — so the replica count is the bill.
  • The environment is the box the apps live in — shared network, and one log destination for everything inside it. You create one per environment-per-region, not one per app, and it costs nothing by itself.
  • A scale rule is the signal Azure watches to decide it needs another replica: CPU, a queue, or here, how many HTTP requests are in flight at once. You give it a floor and a ceiling. A floor of zero means that when nobody is asking, nothing runs and nothing is charged.
  • A managed identity is an Azure identity with no password. Azure holds and rotates the credential, so "no secret" is a property of the object rather than a discipline somebody keeps. User-assigned ones are standalone and outlive the resources that use them, which matters here: every deploy creates a new revision, and a system-assigned identity would be a new principal each time with stale role assignments behind it.
  • A diagnostic setting is a forwarding rule — "send this resource's logs to that workspace". It authenticates as Azure Resource Manager, with no key. That matters here, because the other way to ship these logs needs a shared key this workspace no longer hands out.

Architecture and Workflow

Prerequisites

  • Permissions: Contributor on the workload subscription is enough. This week creates no role assignment, so it does not need User Access Administrator — worth saying, because the following week does.
  • Reader on the resource group holding the Log Analytics workspace. The workspace is read through a data source and never modified.
  • An existing Log Analytics workspace. This week sends its logs to the one week 8 built rather than creating its own. One subscription works fine; the lab splits the workload and the workspace across two.
  • Terraform ≥ 1.10 with azurerm 5.x (1.16.6 was the version that actually ran here). azurerm 5.x requires an explicit subscription_id on every provider block.
  • Four resource providers on the workload subscription — Microsoft.App, Microsoft.Insights, Microsoft.ManagedIdentity and Microsoft.OperationalInsights. The deploy script registers them and waits; registration is per subscription and is a real precondition.
  • Builds on week 8 (the workspace and its table plans). Week 8 does not need to still be deployed, only to exist.

Versions, every variable and the role scopes are in the lab guide on GitHub, which is the reproducible half of this write-up.

Implementation

The goal: a workload that serves real traffic from the internet, runs nothing when idle, and reports to week 8's workspace across a subscription boundary. You need an Azure subscription, an HCP Terraform account, and a Log Analytics workspace to point at.

1. The HCP workspace, created first and deliberately

A new HCP workspace defaults to remote execution, which runs the plan on HCP's servers where there is no Azure CLI. Setting it at birth is one line; discovering it afterwards costs a confusing failure on the wrong machine.

Six resources there, not five — the sixth is the data source reading week 8's workspace. Terraform tracks what it reads as well as what it owns.

2. The Terraform

The replica floor is the week in one argument:

template {
  min_replicas = 0      # the whole point
  max_replicas = 3      # a ceiling, not a target

  cooldown_period_in_seconds = 300

  http_scale_rule {
    name                = "http-concurrency"
    concurrent_requests = 10
  }
}

What production does differently

  • A private registry. This pulls a Microsoft sample anonymously. Production builds its own image into ACR — which adds a registry block pointing at that managed identity, not a password.
  • Builds in CI, on week 7's federated credential, not on a laptop.
  • Something in front of the ingress. External ingress straight to the app is right for a demonstration and rare in production.

Security and Cost

Security

  • No password exists. The app carries a user-assigned managed identity, and a managed identity cannot hold a secret — that is a property of the object, not a discipline anyone keeps.
  • HTTPS only, proven by a 301 rather than assumed from a setting.
  • Named log categories, not allLogs — which is defined by Azure and silently grows when Azure adds a category.
  • The image comes from MCR, so there is no registry credential to hold in the first place.

Cost

The free grant is 180,000 vCPU-seconds, 360,000 GiB-seconds and 2 million requests per subscription per month. This week used roughly 600 vCPU-seconds. A Consumption-only environment carries no fixed hourly fee — though private endpoints and planned maintenance do attract a management charge on either plan, and this week uses neither.

Measured: $0.00. Read from Cost Management after teardown, not from a rate card — sub-lab-dev shows no charges at all for the days this ran. The free grant absorbed the whole week.

Idle replicas bill eight times cheaper than active — but only if the floor is above zero. A floor of zero has no idle state to bill. Keeping one replica warm is the other defensible answer, and the one to pick if 17 seconds is unacceptable.

Troubleshooting and Lessons

The default logging path was impossible.

  • Problem: the default log destination could not be used at all.
  • Root cause: log-analytics wires the environment to a workspace using that workspace's shared key. Week 8 disabled local authentication, so there is no key to hand over.
  • Resolution: azure-monitor plus a diagnostic setting, which authenticates as Azure Resource Manager instead. The cost is that the portal's Logs blade on the app goes dark; queries run against the workspace.
  • Lesson learned: a security decision made one week becomes an architecture constraint the next. The estate is the thing that has to be consistent, not the individual week.

A configuration that never converged.

  • Problem: every plan wanted to set log_analytics_destination_type = "Dedicated" again, forever.
  • Root cause: ARM does not persist that field here, so it reads back null and Terraform sees a permanent diff.
  • Resolution: removed the argument. These logs are resource-specific anyway — proven, not assumed, by AzureDiagnostics holding zero rows while the dedicated table held three.
  • Lesson learned: a plan that is never empty trains you to ignore the diff that matters. Perpetual drift is a bug to remove, not noise to tolerate.

A test that concluded scale-to-zero was broken.

  • Problem: replicas were still above zero at the 300-second mark, with cooldown_period_in_seconds set to 300.
  • Root cause: the cooldown governs when the scaler starts counting down, not when the last replica disappears. Zero came at 602 seconds, roughly twice the configured value.
  • Resolution: poll for zero with a generous ceiling rather than asserting at the configured number.
  • Lesson learned: a timing setting names the start of a process, not its completion. Asserting at the configured value tests the documentation rather than the system.

Key takeaways

  • Scale-to-zero is not free, it is cheap and slow. 16.81 seconds, paid by one user, invisible in any average. Put that number in front of whoever decides whether it is acceptable.
  • A ceiling matters as much as a floor. Zero protects you from idle cost; max_replicas protects you from a runaway one.
  • Last week's security decision is this week's constraint — which is what good security does, and better found in week 9 than in an incident.
