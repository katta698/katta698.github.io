S3 Intelligent Storage Platform: Tiering, Lifecycle, and Cost Automation

S3 costs grow invisibly — objects uploaded once, never moved, billed at Standard rates for years. This platform automates tiering, enforces lifecycle rules, and emails you a daily savings report showing exactly what the automation earned.

Lab Overview

An S3 bucket fills up. Which of those objects is anyone still reading?

The problem. Logs, exports, backups and media all land in Standard and stay there, because nobody goes back to reclassify them. Cost reviews at scale routinely find 60–80% of a bucket cold for months while still billed at the hot rate.

The objective. Let AWS decide where the access pattern is unknown, write deterministic rules where it is known, and mail the bill daily so the result is visible rather than assumed.

The outcome. It deploys and runs. The first daily report comes back empty, for a reason worth knowing before you call it broken.

Architecture and Workflow

Two independent automation paths run on the same bucket. The event-driven path (S3 → SQS → Lambda) tags every new object. The scheduled path (EventBridge → Lambda → SNS) delivers the daily savings report.

Why SQS Between S3 and Lambda?

S3 supports direct Lambda triggers. The production reason to use SQS instead: at high object creation rates, direct S3 → Lambda triggers can throttle or drop events. SQS provides buffering — events queue up and Lambda processes them at its own pace. The DLQ gives you visibility when the tagger fails; without it, a tagging failure would silently disappear.

Why Lambda for Both Functions?

Both workloads fit Lambda’s constraints cleanly. The object tagger: event-triggered, stateless, completes in under a second, essentially zero base concurrency. The cost reporter: runs once per day, needs about 5 seconds to call CloudWatch and SNS, produces no output beyond the email. Neither workload has duration (ECS), parallelism (Batch), or orchestration (Step Functions) characteristics. Lambda is the right tool here — not because it was used in prior weeks, but because the workload shape matches.

Implementation

Step 1 — Terraform Structure

Two Terraform modules under week-08-s3-intelligent-storage/terraform/modules/:

  • s3-storage — the bucket, IT config, lifecycle rules, and bucket notification
  • cost-automation — SQS, DLQ, both Lambdas, EventBridge rule, SNS topic, IAM roles, CloudWatch alarm

The two modules began with a circular dependency. Both now take the bucket name as a variable and build the ARNs themselves.

HCL 
locals {
  account_id     = data.aws_caller_identity.current.account_id
  name_prefix    = "${var.project}-${var.environment}"
  bucket_name    = "${local.name_prefix}-${local.account_id}"
  bucket_arn     = "arn:aws:s3:::${local.bucket_name}"
  sqs_queue_name = "${local.name_prefix}-object-events"
  sqs_queue_arn  = "arn:aws:sqs:${var.aws_region}:${local.account_id}:${local.sqs_queue_name}"
}

Neither module output feeds the other — Terraform can plan and apply both in parallel with no dependency graph cycle.

Step 2 — S3 Intelligent-Tiering Configuration

Intelligent-Tiering is a bucket-level rule with no prefix filter, so it covers every object. Archive Instant activates at 90 days without access, Deep Archive at 180.

HCL 
resource "aws_s3_bucket_intelligent_tiering_configuration" "main" {
  bucket = aws_s3_bucket.main.id
  name   = "EntireBucket"

  tiering {
    access_tier = "ARCHIVE_ACCESS"
    days        = var.intelligent_tiering_archive_days  # 90
  }
  tiering {
    access_tier = "DEEP_ARCHIVE_ACCESS"
    days        = var.intelligent_tiering_deep_archive_days  # 180
  }
}

Step 3 — Lifecycle Policies

Three lifecycle rules on the same bucket:

  • logs/ prefix rule — Standard-IA at 30d, Glacier Instant Retrieval at 90d, delete at 365d
  • AbortIncompleteMultipartUpload — kills orphaned upload parts after 7 days (silent cost if skipped)
  • NoncurrentVersionExpiration — expires old versions after 30 days (versioning is on; without this, every overwrite retains prior versions forever)

Step 4 — SQS + DLQ + Lambda: object_tagger

The queue policy allows SendMessage only from this bucket. The Lambda reads the queue, classifies each object by prefix and tags it; what it cannot process lands in the dead-letter queue.

Python 
def classify_object(key: str) -> str:
    key_lower = key.lower()
    if key_lower.startswith("logs/"):
        return "logs"
    if key_lower.startswith("data/"):
        return "data"
    if key_lower.startswith("media/"):
        return "media"
    if key_lower.startswith("archive/"):
        return "archive"
    if any(key_lower.endswith(ext) for ext in [".log", ".txt", ".csv"]):
        return "logs"
    return "data"

Step 5 — EventBridge + Lambda: storage_cost_reporter

A daily EventBridge rule invokes the reporter, which reads BucketSizeBytes per storage tier from CloudWatch and publishes the total to SNS.

Troubleshooting and Lessons

Problem. The first apply created 24 of 25 resources, then failed with InvalidArgument: Unable to validate the following destination configurations on the bucket notification.
Root cause. AWS validates the SQS queue policy before it will accept a bucket notification. The storage module and the cost-automation module had no dependency between them, so Terraform applied them in parallel and the notification tried to write before the queue policy had propagated.
Resolution. depends_on = [module.cost_automation] on the storage module, which serialises the two. The second apply added the missing resource with no change to the code.
Lesson. This is invisible at plan time — the plan succeeds because the queue will exist by apply. A module-level depends_on is the fix; a sleep is a workaround that passes for the same reason the plan did.

Problem. After a successful aws sso login, every command still failed with "Credentials were refreshed, but the refreshed credentials are still expired."
Root cause. ~/.aws/credentials carried a [default] section header whose keys were all commented out. That file takes precedence over ~/.aws/config, so an empty section was enough to shadow the SSO profile entirely.
Resolution. Removed the section header, put the SSO configuration in the [default] profile in config, and cleared both caches.
Lesson. A section header shadows the other file even when every value under it is a comment. The header alone is the configuration.

Cleanup and Key Takeaways

Cleanup

Versioned Buckets Cannot Be Destroyed Directly

terraform destroy fails on a non-empty versioned bucket: every object version and delete marker must go first.

The repo's cleanup.sh, and the destroy workflow that calls it, empty the bucket before destroying it.

bash 
# Empty the versioned bucket before HCP destroy
BUCKET=$(aws s3api list-buckets --query "Buckets[?contains(Name,'week-08-s3-storage')].Name" --output text --profile personal)
bash week-08-s3-intelligent-storage/scripts/cleanup.sh $BUCKET

# Then trigger destroy from HCP Terraform UI: week-08-dev → Actions → Start destroy plan

Key Takeaways

  1. Intelligent-Tiering and lifecycle are not either/or. Tiering for patterns you do not know, rules for the ones you do.
  2. The unglamorous rules save the most. Aborting incomplete multipart uploads and expiring noncurrent versions remove storage nobody knows they are paying for.
  3. Put a queue between S3 and Lambda. A direct trigger works at low volume; the queue gives buffering, retries and a dead-letter queue.
  4. S3 storage metrics lag about 24 hours. Anything reading them on day one reports zero, correctly.
  5. Some ordering only AWS knows about. S3 validates the queue policy before accepting a notification, which no plan can see.
