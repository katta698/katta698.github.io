Data

The data platform, measured

I started as a database administrator — Oracle, SQL Server, MariaDB and MongoDB across more than a hundred production instances — then moved to Azure, and then to AWS. The clouds changed. The thing underneath them did not: somebody still has to get the data in, keep it, make it mean something, and answer for it when the number is wrong.

Six stages of that work, measured against what the three clouds actually shipped over the last 365 days. Everything with a number refreshes itself; everything that is my judgement says so.

The file formats are not in that race, and are counted separately. An Iceberg table is usually made of Parquet files — the table format supplies transactions, schema evolution and time travel, the file format supplies the columnar bytes underneath. Ranking them together invites a reader to choose between a thing and the material it is built from. Over the same window: Avro 2, Arrow 2, Parquet 1, ORC 0.

Who does what

Editorial, and the titles vary by company. What does not vary is the work, which is why the stages come first and the titles hang off them.

  • Data engineer — ingest · store · transform
    Moves and shapes data, owns the pipelines and whatever wakes up at 3am. Lives in SQL, Python and Spark, and increasingly in Terraform.
  • Analytics engineer — transform · serve
    The role that did not exist ten years ago. Owns the models between the raw tables and the dashboard — dbt, tests, documentation, semantics. Closer to software engineering than to analysis.
  • Data analyst — serve · decide
    Answers the question that was asked and, usefully, the one that should have been. SQL and a BI tool, and more influence on decisions than the org chart suggests.
  • Data scientist — decide
    Statistics and modelling where an answer has to be inferred rather than queried. The part of the field that AI tooling has changed most in two years.
  • Platform engineer / DBA — store · govern
    Still here, under a different title. Capacity, recovery, cost, security and the question of whether that restore has ever actually been tested.

Data quality, as checks that can fail

“Ensure data quality” is not a plan. These six are, because each is an assertion a pipeline can run and stop on. Same discipline this site’s own publishing checks use: a check that cannot fail is worse than no check.

Freshness

A load arrived for the partition that was due, and it arrived on time.

The naive version of this check — an aggregate with a HAVING and nothing else — returns no rows over an empty table, so it reports success exactly when the load never ran at all. Drive it from the partitions you expected and outer-join what arrived.

SELECT e.load_date, MAX(o.loaded_at) AS newest
FROM   expected_partitions e
LEFT   JOIN orders o ON o.load_date = e.load_date
WHERE  e.load_date = CURRENT_DATE
GROUP  BY e.load_date
HAVING MAX(o.loaded_at) IS NULL
    OR MAX(o.loaded_at) < CURRENT_TIMESTAMP - INTERVAL '2' HOUR;

Row-count delta

Today’s load is within a band of the trailing average.

Catches the half-written load and the duplicated one, which are the two common shapes of a broken job.

WITH daily AS (
  SELECT load_date, COUNT(*) AS n
  FROM   orders GROUP BY load_date
), recent AS (
  SELECT AVG(n) AS avg_n FROM daily
  WHERE  load_date >= CURRENT_DATE - 7
    AND  load_date <  CURRENT_DATE
)
SELECT d.n, r.avg_n
FROM   daily d, recent r
WHERE  d.load_date = CURRENT_DATE
  AND  d.n NOT BETWEEN 0.8 * r.avg_n
                   AND 1.2 * r.avg_n;

Null rate

A column that is never null stays never null.

An upstream rename usually arrives as a column going entirely null rather than as an error.

SELECT COUNT(*) AS missing_customer_id
FROM   orders
WHERE  load_date = CURRENT_DATE AND customer_id IS NULL
HAVING COUNT(*) > 0;

Referential

Every foreign key resolves.

The join that silently drops rows is a wrong number, not a failed job.

SELECT o.order_id
FROM   orders o
LEFT   JOIN customers c ON c.customer_id = o.customer_id
WHERE  o.load_date = CURRENT_DATE
  AND  c.customer_id IS NULL;

Schema drift

Columns and types are the ones the model expects.

Both directions. A one-way EXCEPT sees a column that appeared and is blind to one that vanished, which is the half that breaks consumers downstream, later, with no trace back to here.

WITH live AS (
  SELECT column_name, data_type FROM information_schema.columns
  WHERE  table_name = 'orders'
), agreed AS (
  SELECT column_name, data_type FROM orders_contract
)
SELECT 'unexpected' AS drift, column_name, data_type
FROM  (SELECT * FROM live EXCEPT SELECT * FROM agreed) x
UNION ALL
SELECT 'missing', column_name, data_type
FROM  (SELECT * FROM agreed EXCEPT SELECT * FROM live) y;

Distribution

The shape of the data has not moved more than it should.

The only one that catches a correct pipeline carrying wrong data, which is the failure nobody notices for a quarter.

WITH today AS (
  SELECT AVG(amount) AS a FROM orders WHERE load_date = CURRENT_DATE
), baseline AS (
  SELECT AVG(amount) AS a, STDDEV(amount) AS s FROM orders
  WHERE load_date BETWEEN CURRENT_DATE - 30 AND CURRENT_DATE - 1
)
SELECT today.a AS today_avg, baseline.a AS baseline_avg
FROM today, baseline
WHERE ABS(today.a - baseline.a) > 3 * baseline.s;

Each one returns rows only when it fails, which is the whole design: a check that returns a number needs somebody to decide whether the number is bad, and nobody ever does. ANSI SQL — they read the same on Snowflake, BigQuery, Redshift or Postgres, and the interval syntax is the one thing your engine will argue with.
