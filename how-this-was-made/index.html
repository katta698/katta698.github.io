How this was made

No framework, no build server, no database. This is plain HTML, CSS and JavaScript on GitHub Pages — the same free static hosting anybody gets with a repository — and a pile of Python that writes the pages before they ship.

Every number below is counted from the repository when this page is built, not typed in. That is the rule the whole site runs on: if a figure is on a page, something measured it.

What happens when I publish

A post is a file. Everything a reader sees is built from it, which means the pages can always be thrown away and made again — and are, on every publish. Here is the whole trip a post takes, from the file to your screen.

  1. The idea a deck chair, usually

    It starts away from the desk. Somewhere quiet, a laptop, a coffee, and something worth writing down before it goes.

    no ticket, no sprint

  2. Write it posts/arch-042-....html

    One file per post, written by hand. It is the only thing here that is not generated, and every page a reader sees is built from it.

    1 file, by hand

  3. Check the draft prepublish.py

    Before anything is built: are the claims supported, do the links resolve, does the page have the structure its series expects. A post with a dead citation does not get to become a page.

    runs first, refuses early

  4. Build the site sync_blog.py

    One file becomes every post page, the index, the paged archive, the tag and year data, the RSS feed, the sitemap and the service worker — each stamped with a hash of the shared CSS and JavaScript so nobody is served last week’s stylesheet.

    255 posts → 279 pages

  5. Open it in a browser preflight.py

    50 checks drive a real browser: does the header hold still, does the music button actually play, does a filter filter, is every link alive. If one fails the push is refused — the change never leaves this machine.

    50 checks, ~12 minutes

  6. Ship it git push

    GitHub Pages serves the files directly. No server to deploy, no container to restart, nothing to fall over at 2am.

    static files, straight out

  7. Then it runs without me .github/workflows

    This is the part that buys the time back. Seven jobs on a clock read the clouds’ own status, release feeds and event directories, rebuild the pages and commit them — so What’s new, Live status, Cloud events and the Intelligence hub are current whether or not I open a laptop.

    7 jobs, 4 pages, 0 hands

  8. Ask it anything the ask terminal

    And the archive answers for itself. A question is matched against what is actually written in these posts and the answer cites the post it came from — retrieval first, so it can say “nothing here covers that” instead of inventing something.

    grounded in 255 posts

What runs before anything ships

53 checks, in a real browser, on every push. They do not read the code — they open the pages and look: does the header hold still, does the music button actually play, does a filter filter, does every link still resolve, is each page asking for the current stylesheet. If one fails, the push is refused. It costs about twelve minutes, which is the price of not finding out from a reader.

Ask it anything

The terminal on the portfolio answers questions over these posts rather than from a model’s memory: the question is matched against what is actually written here, and the answer cites the post it came from. If nothing here covers it, it says so instead of inventing something.

Why it is built this way

Static files cannot be hacked through a plugin, cost nothing to serve, and load on a bad connection. Nothing here needs a server to be running, a subscription to be paid or a database to be backed up. In ten years these pages will open the same way, because they are just files.
