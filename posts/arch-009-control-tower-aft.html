Business Challenge

A fintech company has 12 AWS accounts managed by a single platform engineer running a bespoke Python script that calls Organizations and Service Catalog APIs. New account requests take two weeks: manual email approval, manual SCP attachment, manual baseline Terraform apply, manual IAM Identity Center assignment. Three engineers are waiting on accounts right now.

Six months from now, that same platform engineer estimates they will have 60 accounts. The script won't scale. There is no drift detection. When someone manually modifies a guardrail or deletes a baseline IAM role in an account, nobody knows until an audit. The platform team's answer is to build a proper account vending machine — an internal tool with its own database, approval workflow, and Terraform pipeline.

That project is scoped at four months. The real answer takes three weeks with Control Tower and AFT.

Architecture

Control Tower with AFT has three distinct layers. Understanding which layer owns which responsibility is what separates a clean implementation from one that fights itself.

Layer 1: Control Tower landing zone

Control Tower sets up the foundational structure: a management account, a Log Archive account, an Audit account, and an OU hierarchy. It deploys mandatory guardrails — preventive controls (Service Control Policies) and detective controls (AWS Config rules). Controls come in three types: preventive (SCPs, block before they happen), detective (Config rules, detect after the fact), and proactive (CloudFormation hooks, block non-compliant infrastructure before it deploys — CloudFormation-managed resources only).

Each control has a guidance level: mandatory (always enabled), strongly recommended (off by default, one-click to enable), or elective (off by default, opt-in per OU).

Layer 2: Account Factory for Terraform (AFT)

AFT is a Terraform module — not a separate AWS service — that runs in a dedicated AFT management account inside your landing zone. When you merge an account request into the account-request repository, a CodePipeline runs, calls the Control Tower Account Factory API to provision the account, and then runs your customisations.

AFT works with four Git repositories:

  • account-request — one Terraform file per account; merging a new file triggers provisioning.
  • global-customizations — Terraform/bash that runs in every account, every time (break-glass role, GuardDuty enable, default VPC delete, mandatory tags). Must be idempotent.
  • account-customizations — per-profile Terraform that runs only for accounts referencing that profile (sandbox, production, data-platform).
  • account-provisioning-customizations — Lambda hooks that run during provisioning itself for pre-provisioning validation and post-provisioning RAM share acceptance.

CodeCommit is no longer available to new AWS customers (closed July 2024). Use GitHub, GitLab, or Bitbucket — all three are supported via native CodePipeline source integrations. Configure this at deployment time.

Why This Architecture Holds Up

Control Tower's detective controls surface manual guardrail changes in the dashboard within 24 hours. Mandatory preventive controls make the highest-risk actions (disabling CloudTrail, modifying the log archive) impossible from inside the account regardless of IAM permissions.

When you update global-customizations, re-invoking the aft-invoke-customizations Step Function rolls out the new baseline to all accounts in parallel. AFT runs at most 5 customization pipelines concurrently and queues the rest. SCPs enforce non-negotiable security posture at the Organizations level — they cannot be bypassed by account-level IAM, including root.

Key Architecture Decisions

  • OU design drives SCP blast radius. Design the OU hierarchy to match your policy segmentation requirements before provisioning a single account. A flat structure gives coarse SCP control; a deeper structure gives fine-grained policy without per-account SCP management.
  • AFT requires Terraform 1.6.1 or later. Confirm this constraint before committing to AFT if your organisation standardises on an older version.
  • The AFT management account is a high-trust target. It has cross-account roles into every managed account. No human IAM users, MFA on root, CloudTrail enabled, access logged.
  • Global customizations must be idempotent. Re-invocations run global-customizations again in every targeted account. Write every step assuming it will run ten times.
  • Start with elective controls disabled. Enable mandatory controls day one. Add elective controls one at a time with a remediation plan for each.

Closing Thought

The fintech company's platform engineer finished the AFT deployment in 11 days. The first account request merged on day twelve and provisioned in 34 minutes. The bespoke vending script project was descoped. The four months of engineering went to the developer portal, the Slack integration, and the cost anomaly alerting that fires into the new account on day one. That is the interesting work. Control Tower and AFT are infrastructure for that work, not the work itself.
