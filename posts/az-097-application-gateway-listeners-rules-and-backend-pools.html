Application Gateway: Listeners, Rules and Backend Pools

Four objects in a chain, and the order they are evaluated in is decided by two completely different mechanisms depending on which SKU you are on. On v1 a single basic listener placed first silently swallows every request on its port.

Jayanth Katta Nov 2026 Azure Application Gateway · Networking

Business Challenge

#95 and #96 covered a service that forwards packets without reading them. Application Gateway is the opposite: it terminates the connection, reads the request, and decides where it goes based on what is inside.

That buys routing on hostname and URL path. It also means four objects must line up before a single request reaches anything:

The chain

“A rule binds the frontend Listener, a Backend Setting and a Backend Pool.” — and “One listener can be attached to one rule.”

A listener decides whether a request is accepted. A rule decides where an accepted request goes. A backend setting decides how the gateway talks to whatever it chose. A backend pool is the set of things it can choose from. Misconfigure any one and the symptom shows up at a different link in the chain than the cause.

The sharpest edge is not in any of the four objects. It is in the question of which listener gets asked first — and the answer is different on each SKU.

On v1, a basic listener placed first takes everything

“For the v1 SKU, requests are matched according to the order of the rules and the type of listener. If a rule with a basic listener comes first in the order, it processes first and accepts any request for that port and IP combination.”

A basic listener matches any host. So one rule in the wrong position does not merely take precedence — it consumes every request arriving on that port, and the carefully written multi-site listeners below it are never consulted.

Architecture

Which listener wins

SKUWhat determines orderRecommended configuration
v1The order of the rules and the type of listener. A basic listener first “accepts any request for that port and IP combination”Multi-site rules first, basic rule last
v2Rule priority — an integer from 1 (highest) to 20000 (lowest), unique per ruleGive wildcard and basic listeners a larger number, so site-specific listeners run first

These are not two expressions of one idea. On v1 the ordering is implicit in a list and is a property of the configuration's shape; on v2 it is an explicit integer and is a property of each rule. A v1 configuration reviewed by reading the rules top to bottom tells you the answer. A v2 configuration reviewed the same way tells you nothing — you have to read the priorities.

The v2 guidance also reads backwards on first encounter: “Define wildcard and basic listeners with a priority number greater than site-specific and multi-site listeners”, because a greater number means lower priority. The catch-all should be the last thing consulted, which means it needs the biggest number.

Why This Is an Architecture Decision and Not a Checkbox

Because the backend pool is not confined to your network

#95 recorded a hard constraint on the layer 4 load balancer: a rule can't span two virtual networks, and all frontends and backend instances must be in a single virtual network. Application Gateway has no such rule.

Backends can be anywhere with IP connectivity

“Application Gateway backend pool members aren't tied to an availability set. An application gateway can communicate with instances outside of the virtual network that it's in. As a result, the members of the backend pools can be across clusters, across datacenters, or outside Azure, as long as there's IP connectivity.”

A pool may hold NICs, scale sets, public or internal IP addresses, FQDNs or short names, and multitenant services like App Service and Container Apps. That is a different class of component from the load balancer — closer to a reverse proxy than to a network device — and it is why Application Gateway shows up in hybrid designs where the load balancer cannot.

The qualifications are worth holding onto. Internal IPs as members require virtual network peering or a VPN gateway; on-premises servers require ExpressRoute or VPN tunnels. And scale sets have a step that produces a confusing first deployment: “After you add virtual machine scale sets as a backend pool member, you need to upgrade virtual machine scale sets instances. Until you upgrade scale sets instances, the backend is unhealthy.”

Because HTTP/2 is a client-side feature only

The backend connection is always HTTP/1.1

“HTTP/2 protocol support is available to clients connecting to application gateway listeners only. The communication to backend server pools is always over HTTP/1.1.”

So HTTP/2 here is a client-experience optimisation, not an end-to-end protocol decision, and a backend built to exploit HTTP/2 multiplexing will never see it. Three related details compound that:

  • It works only over TLS. A cleartext upgrade attempt is not downgraded, it is refused: “doesn't support HTTP/2 Cleartext (h2c) protocol upgrade attempts from HTTP/1.1 and returns a 403 Forbidden error”.
  • The default disagrees with itself depending on how you create the gateway. The documented default is disabled; “When you create an application gateway resource through the Azure portal, the default option for HTTP2 is enabled”. That is the same portal-versus-API asymmetry #95 found in probe intervals, in a different service.
  • Dedicated Backend Connection, the feature required for NTLM and Kerberos passthrough, “isn't supported with HTTP/2”.

That last one carries a cost #96 has already made concrete: “each client connection consumes a dedicated SNAT port, which increases the risk of SNAT port exhaustion”. Turning on Windows authentication passthrough converts a connection-pooling proxy into a one-connection-per-client proxy, and the bill arrives in the outbound port budget.

Because the two timeouts are off by a factor of 360

SettingValue
Request timeout, default20 seconds

Derived86,400 ÷ 240 = 360× more patience for a private backend

The connection draining row is the subtle one. Leaving the feature off does not mean there is no draining timeout — it means there is a 30-second one. And a configuration update “will terminate ongoing connections after the connection draining timeout”, so for any workload serving long downloads, an unrelated gateway change cuts transfers at 30 seconds unless somebody raised a setting they were not using.

The documented symptom is specific enough to recognise: “If you observe intermittent 502 errors during deployments, rolling updates, or scale-in events, the connection draining timeout might be too short.”

Because the probe only runs if the whole chain is wired

An orphaned custom probe monitors nothing

“The custom probe doesn't monitor the health of the backend pool unless the corresponding HTTP setting is explicitly associated with a listener.”

A probe is attached to a backend setting; a backend setting is used by a rule; a rule is bound to a listener. Break any link and the probe exists as a resource, appears configured, and is never executed. This is the chain from the opening section producing a failure that is invisible at the object you would inspect.

The parallel with #95 is exact, incidentally: there, an inbound NAT rule needs no probe at all, and probe definitions go unvalidated outside the portal. In both services the health-checking machinery is the part most easily left not actually running.

Because the host header is a decision, not a passthrough

Two settings rewrite what the backend sees. Pick host name from backend address sets the host header to the backend pool member's own name; host name override replaces it with a literal you supply. Both exist because multitenant backends route on the header — App Service being the canonical case, where “an app service can only be accessed through the hostnames that are configured in the custom domain settings”.

The guidance against using them is unusually direct for a feature's own documentation:

“In production environments, it's a best practice to use the same hostname for the client to application gateway connection and application gateway to backend target connection. This practice avoids potential issues with absolute URLs, redirect URLs, and host-bound cookies.”

The failures named there all share a shape: the application generates something containing its own hostname — a redirect, an absolute link, a cookie domain — and that hostname is now the internal one, which the client cannot reach. Rewriting the host header is cheap to configure and expensive to debug, because the symptom appears in the browser several steps later.

TLS to the backend adds a second dependency on the same header: the gateway “uses the incoming request's host header as the SNI” by default and verifies the backend certificate's subject name against it. Override the host header and you have also changed which certificate the backend must present.

Because the affinity cookie is two cookies, and has been since 2020

Session affinity here is gateway-managed and cookie-based, with a default cookie name of ApplicationGatewayAffinity. Since 17 February 2020 there is also ApplicationGatewayAffinityCORS, carrying “SameSite=None; Secure” so that stickiness survives cross-origin requests — and a custom cookie name gets a matching CORS-suffixed twin.

Two operational consequences. The Secure attribute means affinity over CORS “must be sent over HTTPS”, so an HTTP-only workload cannot have it. And gateways in series collide: “if in your network topology, you deploy multiple application gateways in line, you must set unique cookie names for each resource” — a chained-proxy design that works fine until both gateways set a cookie called the same thing.

Because the port ranges are not what you would guess

SKUListener port rangeExceptions
V21 to 64999Port 22 unsupported with Private Link-enabled gateways; port 53
V11 to 65502Port 3389

Neither range reaches 65535, both stop at a different arbitrary-looking number, and the newer SKU has the smaller range. Backend ports, meanwhile, are the full 1 to 65535 — so the restriction is on what the gateway will listen on, not what it will connect to.

One more constraint that shapes deployments: “An application gateway supports one public or one private IP address”, and for dual-stack, four frontend IP configurations total — one public and one private of each family. Public and private IPv4 listeners may share a frontend port on v2; the IPv6 pair may not.

Design Decisions

DecisionChoiceWhy
Reviewing routing correctness Read priorities on v2; read list order on v1 The two SKUs determine evaluation order by entirely different mechanisms, and a v2 config read top-to-bottom tells you nothing.
Placing a basic (catch-all) listener Last on v1; highest priority number on v2 A basic listener matches any host, so first position on v1 means it accepts every request for that IP and port.
Planning listener capacity Design against 100, not 200 200 listeners may exist but only 100 may actively route traffic.
Expecting HTTP/2 to reach the backend It never does Backend communication is always HTTP/1.1; HTTP/2 is TLS-only on the client side and h2c upgrades are refused with 403.

Closing Thought

The load balancer in #95 fails in ways you can reason about from a packet: a hash, a probe, a budget. Application Gateway fails in ways you can only reason about from a chain. The listener accepted or it did not; the rule matched or it did not; the setting rewrote something or it did not; the pool member answered or it did not. Each link is individually simple, and the diagnostic difficulty is entirely in the fact that a break anywhere presents at the end.

That is why so many of this service's documented traps are the same trap in different clothing. An orphaned probe that never runs. A basic listener that starves the listeners below it. A host header override that breaks a redirect three hops later. A connection-draining timeout that applies when the feature is off. In each case the object you would inspect looks right, because it is right — what is wrong is its relationship to something else.

And the asymmetry worth internalising

Everything this gateway does on the client side is modern and configurable: HTTP/2, HTTP/3 in preview, TLS 1.3, WebSockets, custom error pages. Everything it does on the backend side is HTTP/1.1 to a pool of addresses. It is a translation layer, and the translation only runs in one direction.

Which is the right way to size it up against the alternatives. If the decision you need is “this hostname goes here, that path goes there”, this is the service. If the decision is about packets, ports or throughput, the previous two posts describe something cheaper that never opens the envelope.
