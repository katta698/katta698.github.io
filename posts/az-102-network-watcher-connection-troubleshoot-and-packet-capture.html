Network Watcher: Connection Troubleshoot and Packet Capture

One tool names the fault. The other shows you the bytes. Only one of them works on a virtual machine nobody prepared in advance — and that asymmetry is the whole operational story.

Jayanth Katta Nov 2026 Azure Network Watcher · Diagnostics

Business Challenge

The last seven posts built the data path: load balancers, gateways, Front Door, Traffic Manager, and in #101 the question of which to use. Every one of those designs eventually produces the same support ticket. Traffic is not arriving, every dashboard is green, and somebody has to say which of six possible things is wrong before anyone can fix it.

That is the problem Network Watcher's reactive tools exist for, and the reason they are worth knowing before you need them is that the answer is partly decided at build time. Network Watcher itself is free and automatic: “when you create or update a virtual network in your subscription Network Watcher is automatically enabled in your virtual network's region”, with “no impact on your resources or associated charge.” But its two reactive tools no longer have the same prerequisites.

One of them needs something you installed months ago

Connection troubleshoot is now agentless. You “no longer need to install the Network Watcher agent virtual machine extension on your virtual machines to run connectivity tests”, because “all diagnostics are performed using Azure platform APIs.”

Packet capture still requires the agent. It “requires the Network Watcher agent VM extension AzureNetworkWatcherExtension”, which needs outbound TCP to 169.254.169.254 on port 80 and 168.63.129.16 on port 8037, and is “not supported on AKS clusters.”

So at 2am you always have the tool that names the fault, and you only have the tool that shows the packets on machines somebody prepared. Installing the extension “doesn't disrupt, or require a reboot of the virtual machine” — which is the argument for putting it in the image rather than discovering the gap mid-incident.

Of the eight Network Watcher items Azure shipped at Ignite last week, covered in the 16–20 November roundup, most were ergonomics on top of these two tools. The measurement underneath them is what this post is about.

Architecture

Seven diagnostic tools, and the two that are reactive

Network Watcher is three sets of capabilities — Monitoring, Network diagnostic tools, and Traffic — and the diagnostic set has seven members: IP flow verify, NSG diagnostics, Next hop, Effective security rules, Connection troubleshoot, Packet capture, and VPN troubleshoot. The first four answer a configuration question without sending anything. The last three involve the live path.

The distinction worth internalising is between connection troubleshoot and connection monitor, which sound interchangeable and are not. Connection troubleshoot “returns similar information to the connection monitor capability but tests the connection at a point in time instead of monitoring it over time.” One is for an incident; the other is the standing measurement I covered as part of the weekly. Reaching for connection monitor during an outage means building a test group and waiting for its first interval.

Two of those are shaped like a constraint and one genuinely is. One Network Watcher per region per subscription is not a quota to manage — it exists so the service has a handle in the region. But VPN troubleshoot runs one operation at a time per subscription, which means two engineers diagnosing two different gateway connections during the same incident will serialise, and the second will not understand why.

Why This Is an Architecture Decision and Not a Checkbox

Because connection troubleshoot does not return “unreachable” — it names the fault

A reachability test tells you something you already knew. What makes this tool worth the first five minutes of an incident is that it returns a typed fault. There are six fault types — CPU, Memory, GuestFirewall, DNSResolution, NetworkSecurityRule, UserDefinedRoute — and behind them a long list of specific error conditions, each of which maps to a thing a person can go and change.

Reading that list is the fastest tour of Azure networking's real failure modes I know of, because every entry exists because it happened to enough people to need a code:

ErrorWhat it actually means
UserDefinedRouteA route sends traffic to a None next hop — “creating a blackhole routing.” See #78.
UDRLoopThe next hop IP matches the current hop IP, so the route loops.
IPForwardingNotEnabledThe NVA you route through doesn't have IP forwarding on its NIC — the single most common NVA mistake, and the subject of #83.
VnetAccessNotAllowedThe peering link has AllowVNetAccess set to false. The peering exists and looks connected. See #72.
AllowGatewayTransitNotEnabledThe hub side of the peering never enabled transit; the spoke side blames the gateway.
StandardILBOutboundInternetNotAllowed“Standard ILB backends have no default outbound internet access, unlike Basic ILB.” Exactly the trap in #96.
DIPProbeDownThe load balancer's health probe reports the backend as Down — the probe semantics from #95.
MultiNICsInSameSubnetTwo NICs in one subnet, “which can cause asymmetric routing and unpredictable traffic behavior” — with separate codes when weak host send or receive is also on.
SourcePortInUseThe chosen source port is in TIME_WAIT. The network is fine; the socket is not.

It also reports seven distinct virtual machine power states as separate issue types — VMStarting, VMRebooting, VMStopping, VMStopped, VMDeallocating, VMDeallocated, VMNotAllocated. That granularity is not pedantry. “Stopped but still allocated” and “deallocated” lead to different next actions, and “starting” means wait rather than investigate.

Each issue is positioned as well as typed: an Origin of Inbound (the link from the previous hop), Outbound (the link to the next hop) or Local (this hop), a Severity of Error or Warning, and the hop it was found at. Knowing whether the NSG that denied you is on the source side or the destination side is usually the whole answer.

Because a successful TCP ping can be a lie

The guest firewall answers for the destination

“A TCP ping is a unique use case in which, if there's no allowed rule, the firewall itself responds to the client's TCP ping request even though the TCP ping doesn't reach the target IP address/FQDN. This event isn't logged.”

Read that twice. When the guest OS firewall has no rule permitting the traffic, it answers the probe itself — so the handshake completes, the test looks healthy, the packet never arrived, and there is no log entry anywhere to contradict you. If there is an allowing rule, the request reaches the server and the event is logged in the network rules log.

This is why “I can telnet to the port” is not evidence, and why packet capture on the destination is sometimes the only way to settle an argument.

Because packet capture's defaults are a ring buffer, and ring buffers lose things

A standard capture session stops on time or size: the default time limit is 18,000 seconds, which the documentation notes is 5 hours. Continuous capture is the newer mode and behaves differently — it is explicitly a rotating set of files, and “once the file count limit is reached, the oldest file is automatically deleted to allow space for new packets.”

At the defaults the buffer holds 10 × 100 MB = 1000 MB of recent traffic. On a busy VM that is minutes, not a day, and the documentation says so plainly: “captures with high packet volumes might generate large data sizes quickly.” The time limit is therefore a ceiling, not a promise — the session runs for up to seven days, but what survives is only the last N files. If you are hunting an intermittent fault that fires twice a week, raise the file count before you start, not after you miss it.

The ceiling is enormous — 10,000 files at 4 GB addresses 40,000 GB — which is exactly why the VM needs “sufficient space, or the connected storage account must have appropriate quota.” A diagnostic that fills the OS disk of the machine you were diagnosing has made things worse.

One more sizing lever worth knowing: 34 bytes per packet captures the IPv4 header alone. For a routing or NSG question that is all you need, and it changes the storage arithmetic by orders of magnitude. For a TLS or application-layer question it tells you nothing.

Because a hardening setting can remove a diagnostic

SAS tokens, and the storage account you locked down

“Packet capture uses shared access signature (SAS) tokens to access the storage account. Key access must be enabled on the storage account to authorize packet capture's SAS tokens. If key access isn't enabled, packet captures can only be saved to the virtual machine's local disk.”

Disabling shared key access is standard hardening guidance and usually correct. It also silently takes away one of two capture destinations, and you find out during an incident, on a VM whose disk may not have room. Decide this deliberately: either keep key access on a dedicated diagnostics account, or plan for local-disk captures and size the disk for it.

Because the AI summary is preview, and documented as fallible

Connection troubleshoot can now generate an AI summary of a test, built “from the same data the test returns” — status, hop issues, NSG analysis, route analysis, fault types — and turn it into likely causes and recommended actions. It needs Azure Copilot enabled for the tenant, and during preview it works in ten regions: Chile Central, Indonesia Central, Israel Central, Israel Northwest, Malaysia West, Mexico Central, New Zealand North, Qatar Central, Taiwan North and Taiwan Northwest.

The documentation's own caution is the right posture, and worth quoting to anyone who wants to wire it into a runbook: “AI-generated content can be incorrect. Check the summary against the detailed test results, and confirm any recommended action before you change your network configuration.” The underlying typed faults are the evidence. The summary is a reading of them.

Closing Thought

The interesting thing about connection troubleshoot's error list is that it is a confession. IPForwardingNotEnabled, AllowGatewayTransitNotEnabled, StandardILBOutboundInternetNotAllowed, MultiNICsInSameSubnet — each of those is a code Microsoft wrote because enough people made that exact mistake that a generic failure message was costing real support hours. The list is a map of where this platform is easy to get wrong, published by the people who see every ticket.

Which suggests reading it the other way round. Those sixty-odd codes are the review checklist for a design you are about to ship, not just the output of a test you run after it breaks. If your topology can produce UDRLoop or a None next hop, you will eventually see it.

The one line to take away

A green reachability test is not evidence, because a guest firewall with no allowing rule answers the probe itself and logs nothing. Diagnose with a tool that names the fault, and keep the agent installed so you can look at the packets when the named fault is not enough.
