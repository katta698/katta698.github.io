The week in one paragraph

Networking took the two announcements with the most design consequence, and both landed on material this series covered in the last fortnight: route maps for Azure Route Server went generally available, and Azure Firewall's IPv6 preview picked up application rules. Around them sat an unusually coherent cluster on recovery — Site Recovery for Azure Local, Site Recovery for VMSS Flex, crash-consistent multi-disk restore points, and immutability for SQL point-in-time backups — plus new ransomware recovery guidance for Azure SQL. Two services were put on the retirement list. And the MSRC feed carried zero Azure CVEs in the window, with 25 non-Azure Microsoft advisories filtered out.

Networking: two items that change designs

Route maps for Azure Route Server — generally available

#80 described Azure's BGP as a system you configure rather than one you program: fixed timers, prefix limits, an ASN that is both the default and reserved against you. #83 then used Route Server as one of four NVA high-availability designs, where failover is expressed by advertising a shorter AS path. Route maps are the missing control surface for both, and they are now GA in the public cloud.

What they do is narrow and useful: “Route maps process routing information, not data packets”, applied “in the inbound or outbound direction” on BGP peerings, ExpressRoute and VPN gateway connections, and virtual network connections to peered spokes. Four capabilities: aggregation, filtering, AS path modification and community tagging.

Three constraints are worth reading before planning around them. The first removes a use that looks obvious:

An outbound route map cannot change which path Route Server picks

“Outbound route maps modify route advertisements only and don't influence Azure Route Server's best-path selection, because path selection happens before outbound route maps are applied.”

So AS path manipulation on the way out changes what your peers prefer, not what Azure prefers. #83's active/standby design — one NVA advertising a shorter AS path — works because the NVA does the prepending inbound to Route Server, not because Route Server does it outbound.

The second is a self-defeating combination. Route summarization is listed first among the reasons to use route maps, and then: “Route summarization strips the BGP community and AS path attributes from summarized routes. This limitation applies to both inbound and outbound routes.” Tagging and path control are two of the other three stated benefits, so summarising a prefix range costs you the ability to tag or path-manipulate it. You can have fewer routes or you can have attributes on them.

The third is a default that runs opposite to the rest of this series' subject matter. #84 opened on Azure Firewall's “denies all traffic until you manually configure rules”. Route maps invert it: “When no rule is matched, the default is to allow, not to deny.” A route map built as an allow list by writing permit rules for the prefixes you want does not filter anything — everything unmatched passes. Filtering requires explicit Drop rules, and “to avoid unintended traffic flows, configure rules to match only the routes you intend.”

Two smaller items that will cost someone an afternoon. Route maps “only support 2-byte ASN numbers”, so a 4-byte ASN estate cannot use AS path actions. And the first one you create is not a configuration change:

“The first time you create a route map on an Azure Route Server, the route server undergoes an upgrade that can take up to 30 minutes.”

Finally, the reserved-identifier list is longer than it first appears. Azure reserves eight ASNs against prepending — public 8074, 8075, 12076 and private 65515, 65517, 65518, 65519, 65520 — and eleven BGP communities you must not remove, for nineteen identifiers in total that a route map has to leave alone. 65515 appears here for the third time in this series: #80 found it is simultaneously Azure's default gateway ASN and reserved against your use, and it is now also on the do-not-prepend list.

One more interaction, documented as a hard failure rather than a warning: “Azure Route Server doesn't support point-to-site configurations on Azure VPN Gateway. If the Azure VPN gateway has a P2S configuration, route map creation on Route Server fails.” #74's subject is therefore mutually exclusive with this one in the same virtual network.

Azure Firewall IPv6 now supports application rules — public preview

#84, published on Thursday, spent most of its length on the DNAT → network → application rule pass order and what application rules can match. This week's announcement fills the IPv6 gap in the middle of that: “Azure Firewall fully supports IPv6 traffic in application rules.” The documentation page carries the change already.

The limitations list is the part that matters, because it does not shrink proportionally:

On a dual-stack Azure FirewallIPv6 status
Network rulesFully supported
Application rulesFully supported — new this week
DNS proxySupported
DNAT rulesNot supported yet

IDPSNot supported
Explicit Proxy, IP GroupsNot supported

Read that against #84 and two things follow. Threat intelligence is the control #84 found runs before every configured rule and can block traffic before any rule is processed; IDPS is the Premium engine with over 67,000 signatures. Neither applies to IPv6 traffic. So a dual-stack firewall enforces your rules on both protocols and applies its two signature-based controls to one of them — which means enabling IPv6 on an existing firewall silently narrows the coverage of the Premium features it was licensed for, on the new protocol only.

The second is a direct contradiction of #85's architecture: “Virtual hub (vHub) Firewall isn't supported.” A secured virtual hub cannot do IPv6 firewalling at all. #85 already found that WAF and NVAs must live in a spoke rather than the hub in that architecture; IPv6 is now a third thing the secured hub cannot host.

And there is a familiar shape in the upgrade path:

The third irreversible networking change this series has met

“Reverting a dual stack firewall back to IPv4-only mode isn't supported. This temporary limitation will be removed when dual stack support becomes generally available.”

After #82's routing intent change to the defaultRouteTable and #75's one-way ExpressRoute billing model switch, this is a third case where the Azure portal will let you make a change it cannot undo. At least this one says it is temporary.

One detail connects back to #79's SNAT finding with an exception worth knowing: “For all outbound connections… Azure Firewall applies SNAT by using the firewall instance's IP address. If the destination address is within the IANA-defined unique local address (ULA) range (fc00::/7), SNAT isn't applied. This behavior is by design and can't be changed.” So on IPv6, private-range traffic preserves the source address that #79 showed IPv4 traffic loses — and you cannot turn that off either way.

The immutability item and the ransomware guidance arriving in the same week is the part to notice. Immutable backups are specifically a ransomware control — they defend against an attacker with valid credentials deleting the restore path before encrypting the data. A preview plus a guidance document is Microsoft telling you the threat model it has in mind, and the crash-consistent multi-disk restore points fit the same picture: a restore that is useless because three disks were captured at three different moments is a recovery plan that fails at the only moment it matters.

What I would act on

  1. If you run a dual-stack Azure Firewall, check what your Premium features actually cover. Threat intelligence and IDPS do not apply to IPv6 traffic. Enabling IPv6 on an existing Premium firewall extends your rules to the new protocol and does not extend the two signature-based controls you are paying for. That belongs in the risk register, not in a backlog.
  2. Do not enable dual stack on a firewall you might want back. Reverting to IPv4-only is unsupported until dual stack reaches GA. Test it on a firewall you are willing to rebuild.
  3. If you were planning route maps as a filter, write Drop rules. The unmatched default is allow. A route map containing only permit rules filters nothing, and the failure mode is routes you meant to exclude being advertised normally.
  4. Schedule the first route map, do not slot it into a change window. The first one triggers a Route Server upgrade taking up to 30 minutes. Check for a point-to-site configuration on the VPN gateway first — if one exists, creation fails outright.
  5. Read the two retirements against your own estate now. Fluid Relay and Defender for IoT's OT security are both the kind of dependency that is one team's whole product and nobody else's problem until the date arrives.
  6. Take the immutable-backup preview seriously if you hold regulated data in Azure SQL. It and the ransomware recovery guidance published in the same week are the same thought, and immutability is the control that survives an attacker who has your credentials.
