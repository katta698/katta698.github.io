The week in one paragraph

Azure Front Door had the week: mutual TLS reached general availability, edge actions reached general availability, and gRPC support, JWT validation through Auth Policy and rate limit grouping for the Premium WAF all entered public preview — five of the thirteen Azure Updates entries in the window, from one service. Azure Route Server dual-stack IPv4/IPv6 went to public preview, which matters to anyone running a network virtual appliance hub, and comes with a documentation state worth knowing about before you plan around it. Patch Tuesday landed on 10 November and brought twenty distinct Azure CVEs, with Azure CycleCloud alone accounting for four of them — a sharp contrast with the previous window, which carried none at all. Beyond that the week was Ignite 2026 prologue: a large share of the Tech Community output was session guides and partner announcements rather than shipped capability. Two retirements were posted, one of them with a deadline that had already passed by the time the notice appeared in the feed.

Route Server gets IPv6, and the FAQ has not heard

The announcement is Public Preview: Azure Route Server dual-stack IPv4/IPv6 support, dated 10 November. The tutorial that backs it is explicit: “Azure Route Server IPv4/IPv6 dual-stack mode is in preview”, available in eleven regions, two of which are EUAP canary regions.

The reason to read this one carefully rather than filing it under “IPv6 catch-up” is that the Route Server FAQ, last updated on 3 November, still answers the question directly and in the negative.

Two current pages, two answers

“Does Azure Route Server support IPv6? No. If you deploy a virtual network with an IPv6 address space and later deploy an Azure Route Server in the same virtual network, this breaks connectivity for IPv6 traffic.” — Route Server FAQ

“Azure Route Server IPv4/IPv6 dual-stack mode is in preview… available in preview only in the following Azure regions” — the dual-stack tutorial

Both are probably accurate for what they describe — the FAQ for a Route Server outside the preview, the tutorial for one inside it — but nothing on either page says so, and the FAQ's answer is the one a search engine returns. If you are citing Route Server IPv6 support in a design document this fortnight, cite the region list and the preview note, not the FAQ.

The design detail with the longest reach is that last row of mechanics: IPv6 routes ride multiprotocol BGP over the IPv4 sessions — “the address-family ipv6 unicast block activates IPv6 on the same IPv4 neighbors” — and no separate IPv6 peer is created. So the appliance needs MP-BGP, not a second session, and the Route Server limits are unchanged by the second address family: 16 BGP peers, 4,000 routes per peer, 500 virtual networks, 10,000 prefixes.

Those numbers have an edge to them that is easy to miss. A single peer may advertise 4,000 routes and there are 16 peers, so one deployment can be offered 64,000 routes — but the ceiling towards an ExpressRoute circuit with branch-to-branch enabled is 1,000, four times less than one peer alone may send. Dual-stack does not change that arithmetic; it gives you a second address family to spend it on.

Worth remembering alongside it: “Azure Route Server system routes for traffic related to virtual network, virtual network peerings, or virtual network service endpoints, are preferred routes, even if BGP routes are more specific”. The appliance does not win against a service endpoint route by advertising a longer prefix, in either address family.

Front Door took five of thirteen

Thirteen Azure Updates entries landed in the window and five of them were Front Door: mutual TLS generally available, edge actions generally available, and native gRPC, JWT validation with Auth Policy and WAF rate limit grouping in public preview. Two of them change how an edge is secured rather than what it can serve.

Mutual TLS, now generally available on Premium

“Mutual TLS (mTLS) authentication, also known as client certificate authentication, is generally available in Azure Front Door Premium”, validating certificates at the edge before a request reaches an origin. Four modes, and the gap between them is larger than the names suggest.

ModeWhat Front Door does
Client certificate required and validatedFull validation — presence, validity, revocation, root CA chain and SAN/CN list — then forwards X-Azure-ClientCertificate to the origin
Client certificate required but not validatedDrops requests with no certificate, validates nothing else. The origin must perform all validations
Client certificate validation if presentedFull validation when a certificate is present; passes the request through for origin validation when it is not
mTLS passthrough to originNo validation at all. The origin does everything

Three of those four leave real validation work at the origin, so “mTLS is enabled” is not a statement about security posture until you know which mode. The operational constraints are where this gets expensive to retrofit:

  • No caching. “When you enable mTLS, you can't enable caching on routes or rules engine route overrides with caching” — deliberately, to stop cached content reaching unauthenticated clients. A CDN that cannot cache is a reverse proxy.
  • Endpoint-level gating comes first. mTLS must be enabled on the endpoint before the custom domain, and “you can't associate domains with mixed state of mutual authentication to the same endpoint”. So the unit of migration is an endpoint, not a domain.
  • Downtime in both directions. Turning it on for an existing domain requires disassociating and reassociating the domain; turning it off does too. The documented advice is to enable it on new domains and new endpoints.
  • Certificate plumbing. A root CA alone, or a root plus up to three intermediates, PEM-encoded and under 25 KB, with no auto-rotation and two certificates attachable for rollover. A client chain of more than five certificates including the leaf is rejected outright as ClientCertTooLongChain.

And one item that is a calendar problem rather than a configuration one: Front Door checks Extended Key Usage, “due to industry changes, public certificate authorities (CAs) soon stop issuing client authentication certificates with the required EKU”, and the documented remedy is to move to a private CA. Anyone planning mTLS on Front Door with publicly issued client certificates is planning around a supply that is being withdrawn.

Rate limit grouping: the preview that changes what a threshold means

This is the item I would read first. Until now a Front Door WAF rate limit rule counted per socket IP address. The preview adds four more groupings — country/region, AS number, JA4 client fingerprint, and None, which counts every matching request together — on Premium only, with socket IP remaining the generally available default.

The motivation is stated without euphemism: a per-IP limit “is less effective against distributed attacks, in which a botnet spreads its traffic across thousands of IP addresses so that each one stays under the threshold”. Grouping by JA4 fingerprint counts clients that negotiate TLS the same way as one, regardless of address.

The threshold is not the limit, and this is the sentence to internalise

“For every grouping, each Azure Front Door edge location keeps counts separately and doesn't aggregate them globally… consider a rule that groups by country/region with a threshold of 1,000 requests per minute. If requests from one country/region arrive at three edge locations, each edge location allows up to 1,000 of them per minute, so up to about 3,000 requests per minute from that country/region can be allowed in total.”

That was always true of per-IP rules and barely mattered, because one client's traffic usually lands at one edge. It matters enormously for a grouping, because a country, an ASN or a popular browser fingerprint arrives everywhere at once. A threshold set from total application traffic “might never be reached at any one edge location” — the rule exists, passes review, and never fires.

The documentation does the honest thing and supplies the sizing method rather than a recommended number: a Log Analytics query over FrontDoorAccessLog for the last 7 days, binned at five minutes, grouped by pop_s so the count matches how the limit is enforced, reporting peak and 99th percentile per fingerprint. Measure for at least a week so daily and weekly peaks are represented.

The fourth column is the risk, and the documentation names it: “A breach affects every client in the group… legitimate users who share that country/region, network, or client software are limited along with the attack traffic”, with the aggravating detail that “popular browsers present the same JA4 fingerprint for very large numbers of users”. Which is why the two pieces of guidance that come with it are deploy with the Log action first, and keep a per-IP rule alongside rather than instead — “a client can change its TLS fingerprint, while IP addresses remain the most expensive attribute for an attacker to change”.

One number worth carrying out of it: the documented JA4 example allows 500 requests per five-minute window, an average of 100 a minute, and sits below the threshold at which the documentation warns enforcement stops being precise — “for a low threshold (for example, less than about 200 requests per minute), you might see some requests above the threshold get through”. So the example is deliberately in the approximate zone, because for a grouped rule the alternative is a threshold nothing ever reaches.

What I would act on

  1. Patch the Azure CLI everywhere it is installed, not just where it is managed. CVE-2026-109457 is remote code execution in the CLI, and the CLI lives on build agents, admin workstations and container images that no platform update reaches. The two DevOps Server remote code execution entries point the same direction: this month's Azure exposure is concentrated in the toolchain rather than the workload.
  2. If you have a Front Door WAF rate limit rule, re-read its threshold against the per-edge-location rule. This applies before you adopt anything new: counts have always been kept per edge location, and the preview makes it consequential. Run the documented Log Analytics query — 7 days, five-minute bins, grouped by pop_s — and compare the 99th percentile at a single edge with the number in your rule. A threshold sized from total traffic is a rule that does not fire.
  3. Treat Front Door mTLS as an endpoint-level migration, not a domain setting. Caching cannot be enabled with it, domains of mixed mTLS state cannot share an endpoint, and both enabling and disabling it on an existing domain cause downtime. The documented path is new endpoints and new domains. Decide that before the certificate work starts, not after.
  4. Check whether your mTLS plan depends on publicly issued client certificates. Front Door enforces an Extended Key Usage check, and public CAs are documented as about to stop issuing client authentication certificates carrying it. The recommended answer is a private CA, which is a PKI project rather than a configuration change.
  5. Do not enable Route Server dual-stack mode on anything you care about yet. It is preview, in eleven regions, two of them canary; the switch is irreversible and takes up to 40 minutes; and the FAQ still answers “no” to the question of IPv6 support. Build it in a new Route Server in a test subscription, confirm your appliance does MP-BGP over an IPv4 session, and keep the production hub IPv4-only until the two pages agree.
