This launch is about attribution: putting the identity of the human or workload that started a workflow onto a role session, so a shared role stops being the end of the audit trail. The feature is a good one. The two things worth knowing before you enable it are that switching it on can break federation that currently works, and that the context has a boundary which drops it without stopping the request.

“A missing required source or a present invalid mapped value causes AWS STS to reject the federation request with InvalidIdentityToken.”

Executive summary

The announcement is titled “AWS IAM extends trusted identity propagation to IAM federation and IAM Roles Anywhere, and simplifies it in IAM Identity Center”. What that extension means is that “Trusted identity propagation (TIP) attaches identity context from a trusted source when AWS creates a role session”, and that “Trusted sources include configured external identity providers for AWS IAM federation and X.509 certificates validated against configured trust anchors for IAM Roles Anywhere.”

Two properties make it worth using. The context is immutable — “After AWS attaches the context, callers cannot change it during the lifetime of the role session” — and it survives a role chain without per-role configuration: “If Role B is within the boundary, AWS STS carries TIP context into the new role session without requiring a customer-authored Allow for sts:SetContext.”

What the announcement does not set out is the failure mode on enablement, the shape of the propagation boundary, or the limits: one Subject, up to ten runtime claims, and 128 characters per value.

Architecture

The enablement failure nobody schedules

TIP is configured on the identity provider, which is a shared object. Every role session created through that provider goes through the new validation, and the validation is not advisory. The documentation puts a warning on it: “Before you enable TIP on an IAM identity provider that is already in use, confirm that the identity provider sends every required Subject and mapped Subject type value.”

The asymmetry between the two kinds of mapping is the part to hold on to: “An absent optional runtime claim is omitted from the session. A present optional runtime claim that violates a requirement causes the federation request to fail.”

So a claim your provider never sends costs you nothing. A claim it does send, in a shape TIP rejects, costs you the login. The rejection list includes a source that is present but empty, one that contains only whitespace, one that contains multiple values, one longer than 128 characters, and a mapped Subject type whose value is anything other than user or workload. A multi-valued group attribute in an existing SAML assertion satisfies several of those at once.

The boundary drops context and lets the call through

The propagation boundary is not something you write. AWS derives it from the account that owns the IAM identity provider, and from that account's organization when it has one. What happens at the edge is stated precisely: “AWS STS drops TIP context at the time of the new role assumption. The role assumption can still succeed if the applicable IAM permissions and the target role's trust policy allow the request.”

In an organizationSame organizationCarried
In an organizationStandalone, or a different organizationDropped

This is the right design — identity context should not leak into an organization you do not control — but it means the thing that stops at the boundary is the audit trail, not the access. A cross-organization role chain that works today will keep working, and the CloudTrail events on the far side will attribute the activity to the role.

Assuming a role and calling a resource behave oppositely

The boundary applies to role assumptions that create new session credentials, and a direct request does not create any: “A direct request to an AWS resource in an account that belongs to another AWS organization uses the original session credentials and does not create another role session.”

Reading those two rules together: calling a resource in another organization directly keeps the context, and assuming a role in that same organization loses it. The determining factor is whether new credentials are minted, not where the target lives. For cross-organization resource access the documentation notes that a resource policy can evaluate the TIP condition keys carried in the request.

Service roles use your boundary, not the service's

When a supported AWS service assumes a service role on your behalf, the obvious implementation would check the service principal's account. It does not: “AWS STS does not use the AWS service principal's account.” The same origin account and origin organization decide it, which is what makes the boundary mean one thing across both paths.

The aggregate is the interesting one, because there is no figure to design against: “TIP context shares the capacity of the AWS STS session token with other session data; it does not have a separate fixed aggregate runtime-claim quota in the IAM service model. If the combined session content is too large, the federation request fails with PackedPolicyTooLarge.”

That puts runtime claims in competition with session policies and session tags for one budget. Ten claims at 128 characters is a small addition on its own and a meaningful one on top of a session that is already carrying a packed policy.

Two shapes that will surprise you

For OIDC, nesting is supported exactly one level deep: “AWS STS flattens an object claim nested one level into” a claim/member source, so org/team is mappable from an org object containing team. Deeper nesting is rejected, the object itself is treated as absent, and a flattened key that collides with another claim of the same name is rejected even when neither is mapped.

For SAML, the Issuer context key is not what the name suggests: “For SAML federation, aws:OriginIdentity/Issuer is the lowercase hexadecimal SHA-384 hash of the DER-encoded public key that AWS used to verify the SAML assertion's signature. The resulting value identifies the signing key, not the SAML assertion Issuer element.”

A policy condition written against the entity ID you see in your identity provider's metadata will never match. It also means the value changes when the signing certificate is rotated, so any policy that pins Issuer for SAML is pinned to a key rather than to a provider.

The guidance on the Subject points two ways

On choosing a Subject, the documentation is clear: “AWS recommends that you do not include personally identifying, confidential, or sensitive information in the configured Subject or runtime claims. Consider selecting an opaque, immutable identifier as the Subject.”

And on group-based access, equally clear: “The Subject value must match the corresponding user's Username in IAM Identity Center so that the AWS service can resolve group membership.”

Those are reconcilable only if the Identity Center Username is itself opaque, which for most directories it is not — it is an email address. A deployment that wants group-based authorisation and an opaque Subject has to make the usernames opaque in the directory, and that is a decision about the directory rather than about IAM. The simplification the announcement mentions, adding username alongside user IDs in Identity Center, is the same seam from the other side.

Business value

The problem TIP addresses is real and common: “Multiple human users or workloads can use the same IAM role. The role determines what the session can do, but the role alone does not identify the human user or workload throughout an AWS workflow.”

Every organisation running a CI/CD platform or a shared analytics role has this. One role, many actors, and a CloudTrail record that names the role. The extension to IAM federation matters because it does not require moving to IAM Identity Center first — the existing SAML or OIDC federation path stays, and TIP is added to the provider.

The value is in two places. For authorisation, a policy can now condition on who started the workflow rather than only on which role is being used. For audit, the originator appears in CloudTrail alongside the role. Both are improvements on a role name, and neither requires the role count to grow.

Security considerations

The most important sentence in the documentation is a disclaimer: “TIP context does not grant permissions. IAM policies and supported AWS services determine how to use the context.” Attaching context changes nothing about what a session can do until a policy is written to read it.

The immutability is what makes it trustworthy. Context is attached only after AWS validates the assertion or token, a downstream caller cannot change or remove it, and the namespaces are separated so a customer-mapped runtime claim cannot overwrite the Subject or Issuer.

Two things to hold in mind. First, the origin account and organization keys are AWS-derived and not configurable, which is what makes the boundary a boundary rather than a setting. Second, the context is identity data travelling with requests, and the documentation says so: the identifier and attributes travel to the accounts and Regions your federated users access, and AWS may also process them in default Regions required to fulfil a request. That is the reason behind the recommendation against putting personal data in the Subject.

On audit, note what does not change: “The IAM role remains the AWS principal in the event.” TIP adds the originator next to the principal; it does not replace it.

Cost considerations

No price is attached to TIP in the announcement, and the capability is part of IAM, AWS STS and IAM Roles Anywhere rather than a separate product. The documentation does flag that AWS uses the propagated identifier and attributes to calculate fees and allocate costs to users, which is a statement about attribution rather than about a new charge.

The real cost is operational and it lands once: auditing an existing identity provider's assertions before enabling TIP on it. That is cheaper than the alternative, which is discovering the gap through rejected logins.

Operational considerations

Enable it on a new identity provider, or on a copy, before enabling it on the one your users depend on. The configuration is per provider and the validation is per federation request, so there is no gradual rollout inside a single provider — the change is live for everyone who uses it the moment it is saved.

For verification, CloudTrail is the instrument: “Core origin identity appears in userIdentity.onBehalfOf. Runtime claims appear in userIdentity.transactionContext.IdentityProvider.” The federation event that creates the session records the context, so a single test login tells you whether the mapping produced what you expected.

Reserved target-key suffixes will bite anyone mapping obvious names: subject, subjecttype, identitystorearn, identitycenterinstancearn and identitycentersessionid are taken, in any capitalisation. There is also a derived-key rule worth knowing before it surprises you — a target key ending in IssueTime reserves the matching Age key, so loginIssueTime reserves loginAge, and a claim mapped to an IssueTime key must contain an integer.

Implementation guidance

Start by reading one real assertion or token from the provider you intend to change, and pick the Subject from what is actually in it. The source has to be present on every federation, single-valued, within 128 characters, and stable enough that a policy written against it stays true.

Map runtime claims second and sparingly. Each one is a new way for a federation request to fail, and the ones worth the risk are the ones a policy or an audit query will read — a repository name, a workflow name, an environment. A claim nobody will condition on is pure downside.

Then write the policy conditions. The documentation's advice on this is specific and easy to get wrong: when a policy identifies a specific originator, evaluate Subject together with Issuer. A Subject on its own is only unique within the provider that issued it.

Finally, decide the group-based access question deliberately rather than by default. It is a separate switch, it associates an Identity Center instance with the provider, and it imposes the Username constraint on the Subject you have already chosen.

Best practices

  • Audit the identity provider's assertions before enabling TIP on it, not after.
  • Prefer an opaque, immutable Subject, and resolve the Identity Center Username conflict in the directory rather than by giving up on it.
  • Pair Subject with Issuer in every policy condition that names an originator.
  • Do not pin aws:OriginIdentity/Issuer for SAML to anything you expect to survive a signing-certificate rotation.
  • Map the claims a policy or an audit will read, and nothing else.
  • Confirm a service carries TIP context into its service role credentials before writing a policy that depends on it there.
  • Treat a cross-organization role assumption as an attribution boundary, and plan the audit story on the far side of it.

Who should adopt this and when

Anyone running a shared role with many actors behind it, and particularly anyone whose CI/CD platform federates into AWS through OIDC. The documentation's own example is a GitHub Actions workload using OIDC to assume a shared role, with the repository, workflow and run identity attached to the session. That is the case where a role name is least informative and the gain is largest.

Also worth it for organisations that have stayed on IAM federation rather than moving to IAM Identity Center, because this is the first time TIP is available on that path without changing it.

Not yet, if the downstream services you care about do not consume the context. TIP context attaches regardless, and the audit value is immediate, but the authorisation value depends on service support.

Key takeaways

  • Enabling TIP on a provider already in use can make AWS STS reject federation requests with InvalidIdentityToken. An absent optional claim is harmless; a present invalid one is not.
  • Context is dropped at an organization edge and the role assumption still succeeds, so access continues and attribution stops, with nothing reporting it.
  • A direct cross-organization request keeps the context, because no new role session is created. Minting credentials is the trigger, not crossing an account line.
  • One Subject, up to 10 runtime claims, 128 characters per key and per value, and no separate aggregate quota — the ceiling is the AWS STS session token, shared with session policies and tags.
  • For SAML, the Issuer key is a hash of the signing public key, not the assertion's Issuer element. It changes when the certificate rotates.
  • The Subject should be opaque, and group-based access requires it to equal the Identity Center Username. Both statements are in the documentation.
