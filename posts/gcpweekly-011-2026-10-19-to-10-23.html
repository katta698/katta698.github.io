The week in one paragraph

218 notes across 43 products and five days, down from 236 — and this is a security week rather than a feature week. Three security bulletins landed, every one of them asking something of you, which is notable in itself: last week produced a Critical that required no customer action at all. The headline is a certificate authority whose subordinate CA private keys were generated with insufficient entropy and can be reconstructed, affecting around twenty Google Cloud and Firebase products and every operating system image you maintain yourself. It is rated Medium. Alongside it, a Critical pair of PHP remote code execution flaws, an Istio and Envoy advisory, and a quietly significant GKE fleet-management fix. On the networking side, the item most useful to this series is small: VPC Flow Logs went GA with Cloud NAT drop reasons, which makes port exhaustion a thing you can see rather than infer.

A certificate authority lost its keys

GCP-2026-071, published 23 October, is the week. On Saturday, October 17, 2026, Google received a report from a security researcher regarding the compromise of private keys associated with eight eMudhra subordinate Certification Authority (CA) certificates, including those cross-signed by AAA Certificate Services. The response was immediate and final: consequently, these CA certificates are no longer trusted and are being revoked.

The mechanism is worth stating because it explains why this is not a routine revocation. The private keys for eight eMudhra (emSign) subordinate Certification Authority (CA) certificates were generated using insufficient cryptographic randomness (weak entropy). The keys were not stolen; they were derivable. And the consequence follows directly: this weakness allows a remote attacker with network access to reconstruct private keys, forge trusted TLS certificates, and perform Man-in-the-Middle (MitM) interception against TLS clients, containers, or SDKs that have not yet removed trust in these subordinate CAs.

Google's own position is clear and worth repeating accurately rather than paraphrasing: although Google Cloud infrastructure remains uncompromised, the following Google Cloud and Firebase products, base images, and client SDKs are impacted — a list running to roughly twenty entries including Compute Engine, GKE, Cloud Run, Cloud SQL, AlloyDB, Confidential Space and the gcloud CLI. And on exploitation: security telemetry shows no evidence of exploitation against Google Cloud workloads, and proactive mitigations are in place across Google-managed environments to block and distrust the affected certificate authority certificates.

The part that is yours

Managed services are being handled for you. Everything you run yourself is not: if you manage operating systems or custom container images on Compute Engine, Google Kubernetes Engine (GKE), or Cloud Run, update the trust store via your operating system vendor to revoke trust in the compromised eMudhra (emSign) and AAA Certificate Services certificates. The per-platform routes are named — RHEL has RHSB-2026-012, Ubuntu has USN-8944-1, Debian wants the latest ca-certificates package, Windows wants current updates, and for Container-Optimized OS you upgrade or restart nodes to pick up current COS milestone releases, or apply the cos_ca_cert_mitigation tool. The CLI needs attention too: update to the latest gcloud CLI release to ensure bundled dependencies include updated certificate stores.

It carries CVE-2026-111943 and is rated Medium. That rating is defensible — no evidence of exploitation, mitigations already deployed across Google-managed fleets — and it is also the clearest example I have seen of why severity is the wrong field to triage on. A Medium here means a trust-store update on every self-managed image in the estate, plus a node restart cycle for COS, plus a CLI upgrade. Last week's Critical meant reading one sentence and doing nothing.

Two more bulletins, and the severity lesson repeated

GCP-2026-070, published 21 October and rated Critical: two remote code execution vulnerabilities were found in the open-source PHP language. The scoping sentence is the one to read carefully — while Google Cloud itself is not vulnerable, users of this language running on Google Cloud may be vulnerable — and the affected range is enormous: all PHP versions between 5.4 and 8.5. Fixes are in PHP 8.5.12, 8.4.27, 8.3.36 and 8.2.35, and the instruction is unambiguous: customers should take immediate action to protect their workloads by redeploying their workloads with updated dependencies.

Two mitigations soften it. Some platforms self-heal — some workloads may be automatically patched and updated to the latest PHP if they are on Google App Engine Standard or one of Cloud Run, Cloud Run functions with automatic updates enabled — and there is a way to find your exposure rather than guess at it: customers using Artifact Analysis receive notifications of these vulnerabilities on both new and existing artifacts to help them identify at-risk workloads. It carries CVE-2026-109618 and a second CVE alongside it.

GCP-2026-069, published 19 October and rated Moderate to High: security vulnerabilities were discovered in Istio and Envoy Proxy ( ISTIO-SECURITY-2026-007 ), with four GHSA identifiers and a pointer rather than instructions — for instructions and more details, see the Cloud Service Mesh security bulletin. Anyone running Cloud Service Mesh has to follow that link; the bulletin itself does not carry the remediation. Worth noting this is the third consecutive week with an Envoy-related advisory, after the DoS in GCP-2026-067.

So three bulletins, three severity bands, and all three require customer work — against last week's single Critical that required none. Two weeks is not a trend, but it is now twice that the rating has told me nothing about whether to open a terminal.

NAT port exhaustion becomes visible

The smallest item in the window is the one that changes something for this series. General Availability: VPC Flow Logs adds the following metadata annotations and packet drop reasons for Cloud NAT — the annotations being metadata annotations: connection.nat_ip , connection.nat_port , and nat_gateway_details, and the drop reasons drop reasons: NAT_ENDPOINT_INDEPENDENT_CONFLICT , NAT_OUT_OF_CONNECTIONS , and NAT_OUT_OF_PORTS.

Those three drop reasons are the answer to a question this block of the architecture series kept running into. #69 established that Google Cloud has two different drop behaviours and that telling them apart is most of the diagnosis: an empty route model returns an ICMP unreachable, while a subnet route matching an address with nothing live behind it drops in silence. NAT exhaustion has always been in the second category — a connection that simply does not happen, with nothing in the path to say why. Naming NAT_OUT_OF_PORTS and NAT_OUT_OF_CONNECTIONS as flow-log drop reasons converts that from an inference about capacity into a record you can query, and connection.nat_ip with connection.nat_port makes the translation itself visible rather than opaque.

Cloud Armor shipped two security notes the same day, both WAF ruleset maintenance: fixes and enhancements to the preconfigured WAF v33-stable rulesets and separately to the stable rulesets for v3.0. Routine, and the kind of thing worth knowing happens continuously if you have tuned rules against a specific ruleset version.

Platform, data and the rest

A GKE fix worth noticing for what it was. A security issue in GKE fleet management that could have allowed unauthorized configuration changes to clusters registered to a fleet has been resolved, and the fixes are rolled out to all regions, and no action is required. Unauthorized configuration changes to fleet-registered clusters is a serious class of problem, disclosed as a one-line Fixed note rather than a bulletin. No action needed, but worth logging that it happened.

The week's only Breaking tag. Gemini 2.5 Pro has been discontinued for in-country Gemini Enterprise app deployments in Canada and Japan, and the fallback is automatic: agents and chat sessions in these regions that previously used Gemini 2.5 Pro automatically switch to in-country Gemini 3.5 Flash. The scope is narrow — Gemini 2.5 Pro remains available in the global , us , and eu regions — so this is a data-residency consequence rather than a general withdrawal. An automatic switch to a different model class is the sort of change that does not break a deployment and does change its behaviour.

A dated billing change with four days of notice. On October 26, 2026, Gemini 4 Argon will replace Gemini 3.8 Flash as the default model for new AlphaEvolve experiments, published 22 October. The money sentence is explicit: from that date, new experiments that use the default model are billed at Gemini 4 Argon token prices instead of Gemini 3.8 Flash token prices. Opting out is a one-line change — to keep using Gemini 3.8 Flash, specify gemini-3.8-flash in the models field — and existing work is safe, since experiments created before October 26, 2026 keep the model recorded in their configuration. Anything that relies on the default and has a budget attached needs looking at before Monday.

Data. Spanner supports approximate aggregate functions for both GoogleSQL and PostgreSQL dialects, which produce statistical estimates of distinct counts, allowing you to compute results faster and save resources on large datasets compared to exact aggregation — HyperLogLog++ and sketches, for the cases where an exact distinct count is not worth what it costs.

Volume, for context. Looker and Container-Optimized OS each contributed sixteen notes, Contact Center as a Service ten, and Apigee X and Cloud Service Mesh seven apiece. The COS run is the usual milestone-release pattern the inventory rolls up rather than deduplicates, and this week it is carrying the CA mitigation described above.

What I would act on

  1. Update the trust store on every image you build yourself. GCP-2026-071 is the week's real work: RHEL via RHSB-2026-012, Ubuntu via USN-8944-1, Debian via the latest ca-certificates, Windows via current updates, and COS by upgrading or restarting nodes or applying cos_ca_cert_mitigation. Managed services are Google's problem; your base images are not.
  2. Upgrade the gcloud CLI, including on build agents. The same bulletin asks for it explicitly, and CI runners are the copies nobody remembers to update.
  3. Find your PHP exposure with Artifact Analysis rather than by asking teams. Everything between 5.4 and 8.5 is affected, the fix versions are named, and App Engine Standard and Cloud Run with automatic updates may already have handled it — so the useful first step is an inventory, not a redeploy.
  4. If you run Cloud Service Mesh, open the CSM bulletin today. GCP-2026-069 deliberately does not carry the remediation, and this is the third week running with an Envoy advisory.
  5. Check AlphaEvolve experiments that rely on the default model before 26 October. Four days of notice, and the consequence is a different token price rather than an error.
  6. Turn on the new Cloud NAT drop reasons if you run Cloud NAT at any scale. NAT_OUT_OF_PORTS in a log is worth a great deal more than a theory about port allocation.
