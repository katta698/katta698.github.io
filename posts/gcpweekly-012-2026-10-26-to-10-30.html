The week in one paragraph

Two hundred and thirty-one notes across Monday to Friday, and the two that matter most are both security bulletins describing vulnerabilities that were already closed before anyone outside Google knew they existed. Beyond those, the week's most consequential item is not a feature at all: Cloud DNS published two behaviour changes taking effect on 5 January 2027, one of which alters the order in which private and public zones are consulted. That is the kind of change that breaks resolution in estates nobody touched. The rest of the week was Looker and the agent platforms — Looker alone accounted for 22 notes — plus a steady run of GKE channel releases and Container-Optimized OS rebuilds.

Two bulletins, both already patched

Both of this week's bulletins follow the same pattern, and it is a pattern worth naming because it changes how you should read them.

GCP-2026-074, published 28 October and rated Critical, is a Deserialization of Untrusted Data vulnerability was discovered in the SubWorkflow task in Application Integration versions prior to September 11, 2026. The impact is as bad as that class gets: an authenticated user could use a maliciously crafted serialized object to execute arbitrary code. It carries CVE-2026-93327. And the resolution is already done — this vulnerability was patched on September 11, 2026, with no customer action is required.

GCP-2026-073, published 26 October and rated High, is more directly interesting to anyone who has been following the IAM material in the architecture series: an incorrect authorization vulnerability in Compute Engine versions prior to August 31, 2026 allows a user to exfiltrate disk data without the required IAM permissions. Again closed in advance — this vulnerability was patched on August 31, 2026, and no action is required from you. Compute Engine's own release notes carry the matching line: a vulnerability (CVE-2026-85299) about incorrect authorization in Compute Engine was discovered and has been addressed.

The gap between fix and disclosure

GCP-2026-073 was patched on 31 August and disclosed on 26 October — fifty-six days later. GCP-2026-074 was patched on 11 September and disclosed on 28 October, forty-seven days. Neither gap is unusual or improper; coordinated disclosure after a fix is the correct order. But it does mean a weekly roundup of bulletins is a record of what Google has finished dealing with, not a list of what is currently at risk. The actionable content of both bulletins is the same sentence: no action is required. The useful content is the class of bug — an authorization check that could be bypassed to read disk data without the IAM permission that was supposed to gate it, which is a reminder that an IAM grant is a statement of intent enforced by code.

Cloud DNS changes resolution order in January

This is the item I would put in front of a network team, because it changes behaviour on a date rather than offering a feature. Starting January 5, 2027, CNAME chasing behavior will change so that Cloud DNS follows CNAME chains between public and private zones. The consequence is stated plainly: if your private zones or response policies have overlapping domain names with public CNAME targets, queries might resolve to unintended internal IP addresses or return resolution errors.

The mechanism is a widening of scope. Today, a CNAME answer from a public zone is chased only through public zones and internal DNS; from January, subsequent queries follow the complete VPC name resolution order: response policies, private zones, forwarding or peering zones, internal DNS, and public zones. The same widening applies to answers from private zones and from response policy zones. So a name that resolves one way today can resolve to an internal address afterwards, with no configuration change on your side.

Google's own guidance is unusually specific about what to do, which is itself a signal: review your CNAME chasing needs before January 5, 2027, and test your DNS query paths using dig or nslookup to identify CNAME chasing scenarios.

The second DNS change lands on the same date and is narrower: starting January 5, 2027, Cloud DNS will disable full responses to DNS queries of type ANY in public authoritative zones, returning a single resource record instead. ANY queries are mostly used by diagnostic tooling and by reflection-amplification abuse, so the blast radius is small — but any monitoring script that parses an ANY response will stop seeing what it expects.

Networking, IAM and the rest

Three items outside DNS are worth more than an inventory line.

Cloud Armor gained request-body inspection. Cloud Armor supports advanced match conditions to include attributes for inspecting request body content and parameters, and this lets you write custom CEL rules to act on them. Until now, custom rules worked largely on headers, paths and IP attributes; matching on body content moves a class of filtering out of the application and into the edge.

Application Load Balancers got regex URL rewrites. Regular expression URL rewrites ( regexRewrite ) for route rules in URL maps are now generally available (GA) for Application Load Balancers. That removes a standing reason to keep a rewriting proxy in front of a load balancer.

IAM published three new basic roles. The Admin ( roles/admin ), Writer ( roles/writer ), and Reader ( roles/reader ) basic roles are generally available ( GA ). Worth a careful look rather than enthusiasm: the existing basic roles (Owner, Editor, Viewer) are the ones every hardening guide tells you to stop using because they are too broad, and a new set of basic roles is a new set of broad grants. The interesting question is whether these are narrower than their predecessors or merely differently named, and that is a question for the roles reference rather than for a release note.

The volume this week sat in the data and agent products rather than infrastructure. Looker led with 22 notes, including data lineage reaching GA and a Looker-managed Model Context Protocol server going GA. Google Kubernetes Engine contributed 14, almost all channel releases across Rapid, Regular, Extended and the deprecated no-channel track. Gemini Enterprise Agent Platform had 10, Container-Optimized OS 9, and Google SecOps Marketplace 9. Nothing in the firewall, routing or Shared VPC surfaces this series is currently working through changed at all.

What I would act on

  1. Diarise 5 January 2027 and test CNAME chains now. This is the only item this week that can break a working estate without anyone changing anything. Run the dig and nslookup checks Google asks for, and specifically look for names that exist in both a private zone and a public CNAME target — that overlap is the failure condition.
  2. Check whether anything parses ANY responses. Same date, much smaller surface. Monitoring and inventory scripts are the likely callers.
  3. Read the new basic roles before anyone grants one. Three new basic roles reaching GA is the sort of change that gets adopted by convenience. Establish whether roles/reader is narrower than roles/viewer before it appears in a policy.
  4. Nothing to do for either bulletin. Both were patched by Google weeks before disclosure and both say so explicitly. Record them and move on — and note GCP-2026-073's class, because an authorization bypass that reads disk data without the gating IAM permission is a useful argument for defence in depth behind IAM.
