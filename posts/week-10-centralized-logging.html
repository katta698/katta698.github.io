AWS Platform Engineering Lab · Week 10
Centralized Logging Platform: One Query Across Every Account
Every account in an AWS organization hoards its own CloudWatch log groups — so "show me every error across the platform in the last hour" means logging into N accounts and running the same query N times, and log evidence dies with the account that produced it. This platform fixes both with CloudWatch's 2025-era native primitives: cross-account observability (OAM) for query-in-place, and organization-wide centralization rules for durable copies — no OpenSearch cluster, no Firehose pipeline, and the first centralized copy is free.

Lab Overview

"Show me every ERROR across the platform in the last hour." With one account that is a query. With ten accounts it is ten logins, ten consoles and the same query typed ten times — and if one of those accounts is the one that got compromised, its logs are sitting inside the blast radius.

The old fix was expensive enough that most teams skipped it: subscription filters into Kinesis Firehose into an OpenSearch cluster, comfortably $1,000 a month at scale plus someone's half-time job. In 2025 AWS made cross-account querying native and the first centralized copy free. This lab builds the version that exists now — and runs into one feature that was not ready.

Sharing and copying are different tools

OAM answers "query everything, now, for free" but the only copy of the data still lives in the account that produced it. A centralization rule answers "keep evidence that outlives the account" at the cost of storing it twice. Neither replaces the other, which is why this build runs both paths.

Log class is an irreversible choice

The Infrequent Access class halves ingestion cost — $0.25/GB against $0.50/GB — but permanently disables metric filters, subscription filters and Live Tail, and a log group's class can never be changed after creation. The destination groups here stay Standard, because the alarm needs a metric filter and first-copy ingestion is free anyway. IA would have bought nothing and cost the alerting design.

The pattern AWS is retiring

Subscription filters into Firehose into OpenSearch is the architecture AWS is itself sunsetting: the official "Centralized Logging with OpenSearch" solution retires in December 2026, with customers steered to the native capabilities. Worth re-checking a "best practice" diagram against the current platform before rebuilding it.

Architecture and Workflow

  1. Generate. An EventBridge rule in the source account invokes a 128 MB Lambda every five minutes, emitting around 25 structured JSON lines per run with weighted INFO/WARN/ERROR levels.
  2. Land. The function's logging_config routes its output into /platform-lab/week10/log-generator with 14-day retention, rather than the default /aws/lambda/* group, so one group carries the whole story.
  3. Share, and copy. The OAM link makes the source account's logs and metrics queryable from the monitoring account instantly and at no charge. In parallel, the org-wide centralization rule is meant to replicate those groups into the management account, tagging each stream with its source account and region.
  4. Watch the copy, not just store it. A metric filter counts ERROR events in the centralized stream; an alarm fires at five or more errors in five minutes and publishes to SNS. A cross-account dashboard puts that error count next to the source account's own Lambda metrics — the OAM half made visible.

Security and Cost

  • The sink policy is scoped twice. Only accounts inside the organization can link to it (aws:PrincipalOrgID), and only for logs and metrics (oam:ResourceTypes) — no outside account, no other telemetry types.
  • Evidence outlives the account. Centralized copies live where the source account has no write access. That is the whole security argument for physical copies over pure sharing, and it is the half of this build that did not land.
  • No static credentials. HCP authenticates over OIDC, the spoke is reached by role assumption, and the service-linked role bounds what the centralization service can do.
  • Retention as a control. 14 days at source, 30 days centralized. Logs are a liability as much as an asset; unbounded default retention is both a cost leak and an exposure surface.

Troubleshooting and Lessons

"Centralization is currently initializing. Please try again later."

This is the one that did not get fixed. After trusted access was enabled, CreateCentralizationRuleForOrganization returned a ValidationException and kept returning it, retried every few minutes for more than 24 hours, while read APIs on the same service answered normally. No documentation mentions an initialization window at all.

Root cause: never established. Everything checkable was ruled out — the service-linked role exists, trusted access reads On, a delegated administrator was registered, and CloudTrail confirms the calls arrive and are rejected. The console's own wizard accepts the entire configuration and then refuses the final create with the same message, and its "turn off trusted access" button greys out while initializing, so the setting cannot even be re-toggled. One suspect worth naming without claiming it: this organization contains eight closed accounts sitting in their 90-day post-closure SUSPENDED state, and an org-wide provisioning workflow that touches every member account may not enjoy meeting them.

Lesson, which stands whenever AWS finishes: never put an org-wide enablement with an unbounded activation time on the critical path of a build. The OAM half of this architecture was queryable in minutes; the half that depended on an organization-wide backend was not, and no amount of correct Terraform changed that.

The OAM link raced a policy it never referenced

First apply: 15 of 17 resources created, then aws_oam_link failed with AccessDeniedException ... explicit deny in a resource-based policy. The policy was correct — the identical CreateLink call succeeded from the CLI minutes later.

Root cause: Terraform called CreateLink 14 seconds after creating the sink policy, before the resource policy had propagated. The dependency graph permitted it, because the link references the sink's ARN and nothing ordered it after the policy.

Fix: a module-level depends_on = [module.oam_hub] on the spoke. The general shape is worth keeping: when resource A must satisfy a resource-based policy created by resource B, referencing A's parent does not order it after B. Say the dependency out loud.

A new feature has four clocks

Docs, console, CLI and Terraform provider each described this feature slightly differently in the same week — including an undocumented initialization wait. Verify each layer live rather than assuming they agree.

Cleanup and Key Takeaways

The workspace is VCS-connected, so destroy through HCP: week-10-dev → Settings → Destruction and Deletion → Queue destroy plan. Afterwards confirm three things are actually gone: log groups under /platform-lab/week10 in both accounts, the OAM sink and link pair, and the centralization rule. Organizations trusted access is an org-level setting rather than a billed resource — leaving it on costs nothing and saves the initialization wait next time.

  • Sharing and copying are different tools; run both. OAM gives you the query, centralization gives you the evidence that survives the account that produced it.
  • The 2025 primitives deleted a whole architecture. Three billed hops became one native feature. Re-check inherited "best practice" diagrams against the current platform.
  • Log class is irreversible and invisible. Infrequent Access halves ingestion and permanently kills metric filters. Decide per log group, at creation, with the alerting design in front of you.
  • Terraform's graph only knows what you reference. When correctness depends on a policy existing, depends_on is the honest fix rather than a retry loop.
  • Publish the part that did not work. Four of five paths worked; one was refused by AWS for a day with no documented reason. A lab writeup that quietly omits that is a worse artifact than one that names it.
