Security Hub + GuardDuty: Findings That Fix Themselves
A security finding is worthless if it sits in a console nobody watches. This week wires Security Hub and GuardDuty to EventBridge and Lambda so the clear-cut, dangerous misconfigurations — a management port open to the whole internet, a public S3 bucket — get fixed automatically in seconds, while active-threat findings that need human judgement get escalated to a person instead of being touched. The whole thing is tag-gated so it can never surprise a resource you meant to leave alone.

Lab Overview

A security group gets opened to the whole internet on port 22 — someone debugging at 6pm who meant to close it afterwards. GuardDuty and Security Hub are very good at spotting that within minutes. Then the finding sits in a console, because nobody wants to be the person whose automation revoked a rule production depended on.

This lab closes that loop for a narrow, clear-cut set of findings: the fix runs in seconds and the finding is marked resolved, while judgement calls still go to a human. The blast radius is handled by one boring guardrail — nothing is ever modified unless it carries an explicit opt-in tag.

ASFF — one schema for everything

The AWS Security Finding Format is what makes a single pipeline possible. A GuardDuty threat and a failed config control arrive in the same shape, so one set of routing rules and one writeback call cover both.

Classic CSPM, not the unified Security Hub

AWS relaunched a unified Security Hub (v2 APIs) at re:Invent in December 2025, correlating GuardDuty, Inspector, Macie and classic Security Hub into one view. As of mid-2026 the Terraform AWS provider does not stably support it — aws_securityhub_account_v2 is still an open feature request. That costs this build nothing: v2 is a correlation layer above the finding stream and does not change how you react to a finding. Everything here is classic CSPM, which the provider fully supports, and v2 can be enabled alongside it in the console.

Architecture and Workflow

  1. Detect. GuardDuty analyses CloudTrail, VPC Flow Logs and DNS. Security Hub CSPM runs the FSBP standard and ingests GuardDuty's findings, all normalized to ASFF.
  2. Enrich, before routing. A Security Hub automation rule runs inside Security Hub before any EventBridge rule fires, escalating failed controls on resources tagged environment=production to CRITICAL. Downstream paging gets smarter without touching a line of Lambda code.
  3. Route. EventBridge rules match on detail.findings.Compliance.SecurityControlId — EC2.13/14/19 to the security-group remediator, S3.2/3/8 to the S3 remediator — and on the native aws.guardduty event for the threat notifier. Every rule matches Workflow.Status = NEW only, which turns out to be the most important clause in the stack.
  4. Act, but only on opt-in. The security-group remediator revokes just the world-open ingress on high-risk ports; the S3 remediator applies all four Block Public Access settings. Both act only on resources tagged auto-remediate=true. Anything untagged is reported to a human and left exactly as it is.
  5. Write back. Every action is written to the finding via BatchUpdateFindings, so the console reflects reality rather than a backlog of issues that were quietly fixed hours ago. Failed asynchronous invocations land in a dead-letter queue that alarms — a dropped security action is worse than a slow one.

Implementation

ModuleResourcesIts job
securityhub4Account enablement, the FSBP standard subscription, a cross-region finding aggregator, and the automation rule that escalates production findings
guardduty1One detector — foundational sources, Extended Threat Detection included at no extra cost
remediation25Three Lambdas built from one for_each block, each with its own role, policy, log group, EventBridge rule and invoke permission, plus a shared SNS topic, SQS dead-letter queue and CloudWatch alarm

Setting control_finding_generator = "SECURITY_CONTROL" on the account matters more than it looks: it is what populates Compliance.SecurityControlId, the exact field every EventBridge rule keys on. Without it the routing silently matches nothing.

Lambda is the right shape here rather than Step Functions or ECS: each remediation is one or two API calls, stateless, event-triggered, finished in seconds, with near-zero concurrency. Step Functions would earn its place if a remediation needed approval steps or ran for minutes. Neither does.

Security and Cost

The point of auto-remediation is that it acts with no human in the loop, so the safety has to be structural rather than procedural.

  • Opt-in by tag, enforced twice. Mutating remediations only touch resources tagged auto-remediate=true. The function checks the tag, and its IAM policy carries an aws:ResourceTag condition so RevokeSecurityGroupIngress itself refuses on anything untagged. A bug in the code cannot widen the blast radius.
  • Least privilege per function. Each Lambda has its own role with exactly the actions it needs. The threat notifier has no mutating permissions at all — it can publish to SNS and nothing else.
  • Surgical and idempotent. The remediator strips only the 0.0.0.0/0 and ::/0 ingress on high-risk ports, leaving scoped rules alone, and treats an already-removed rule as success.
  • No silent failures. Failed invocations go to a 14-day dead-letter queue that alarms. Every action is written back to the finding, so there is always a record of what changed and why.

Troubleshooting and Lessons

The remediator fed itself, about eight times a minute

The S3 remediator began firing indefinitely against one pre-existing untagged bucket, emailing every time.

Root cause: the EventBridge rule matched Workflow.Status of both NEW and NOTIFIED. On the notify path the Lambda called BatchUpdateFindings to set the status to NOTIFIED — and that update was re-emitted as a finding event, which matched the rule again. The automation's own writeback was its trigger.

Fix: match NEW only, so the writeback status falls outside the trigger pattern. This never appeared in synthetic testing; it took the account's real findings to surface it.

The first apply timed out, then undid itself

aws_securityhub_standards_subscription failed with "timeout while waiting for state to become READY".

Root cause: the FSBP standard has roughly 300 controls and sits in PENDING on a cold account for longer than the provider's three-minute default. Each failed apply then disabled and re-enabled the standard, resetting the clock — a loop that looks like a broken resource and is really an impatient one.

Fix: timeouts { create = "15m" }.

The fix was pushed, and the old code ran anyway

A run queued through the HCP API timed out at three minutes again, with the fifteen-minute setting nowhere in evidence.

Root cause: a run created via the HCP API reuses the workspace's most recently ingested configuration version. It does not fetch the new commit, so both runs executed the pre-fix code.

Fix: bind the run to the new commit's configuration version, or let the VCS webhook ingest it first and confirm the run's version matches the commit you intend. "Queue a run via the API" is not "deploy my latest commit".

Cleanup and Key Takeaways

Queue a destroy on the week-11-dev workspace: it disables Security Hub CSPM and the GuardDuty detector and removes the Lambdas, rules, SNS topic and dead-letter queue. A small script tears down the deliberately-insecure test resources. One apply rebuilds the stack in about ten minutes, so destroying is cheap to reverse.

  • Breaking the loop is the whole game. Any find-and-act automation whose action updates the thing that triggered it will feed itself forever unless the writeback status falls outside the trigger pattern.
  • Opt-in, not opt-out. Tag-scoping enforced in both code and IAM is what turns "terrifying" into something you would run in production. An untagged resource is reported, never touched.
  • Fix the mechanical, escalate the judgement calls. Misconfigurations get closed automatically; active threats get a human. Killing the wrong instance mid-incident can be worse than the threat.
  • Know what the pipeline depends on. Security Hub controls need Config recording, and standards take minutes to initialize. Neither is obvious when the symptom is a pipeline that deploys perfectly and does nothing.
  • Real findings find what synthetic events cannot. The feedback loop was invisible to unit tests and obvious within a minute of meeting the account's actual backlog.
