AWS Config Compliance Automation: The Drift Security Hub Never Sees
Security Hub (Week 11) is very good at catching security misconfigurations. It has no concept of a missing cost-allocation tag or a data bucket that was never versioned — those aren't security findings, so nothing watches for them. This week closes that gap with a self-contained AWS Config conformance pack: two rules auto-remediate through AWS-managed SSM documents, one is deliberately notify-only because a tag value can't be safely invented, and a daily Lambda digest reports on all three. Along the way, the account's Config recorder vanished mid-build — not from anything this stack did — and that turned into the week's real lesson.

Lab Overview

Security Hub's FSBP standard checks roughly 300 controls, and by Week 11 it already covered nearly every security-relevant misconfiguration in this account — open ports, public buckets, disabled encryption defaults.

The problem. It has no concept of governance drift. A bucket created without a cost-center tag, or one that was never versioned, is not a security finding — Security Hub simply has no control for either. Nothing watches for it. That kind of drift does not announce itself; it accumulates quietly until a cost-allocation report has a chunk of unattributed spend, or until someone deletes an object from an unversioned bucket and there is no previous version to recover.

The objective. A conformance pack that evaluates governance rules continuously, auto-remediates the safe ones through AWS-managed automation, and reports the rest to a human daily.

The outcome. It works — and produced an unusually dense run of real bugs, none of which terraform validate or the documentation caught.

Governance drift is not a security finding. That distinction is the whole week: Security Hub answers "is this dangerous", Config answers "is this how we said it should be". The second question has no owner unless you give it one.

Config's Scope is either-or. Resource-type filtering and tag filtering cannot combine in one rule. When you need both a type and a tag constraint, scope on the tag alone and let the rule's own logic handle the type.

Architecture and Workflow

  1. An AWS Config recorder captures configuration changes for every supported resource type, continuously and account-wide.
  2. A conformance pack containing three rules evaluates against those configuration items.
  3. required-tags checks everything broadly and is notify-only — it never invents a value.
  4. Two S3 rules evaluate only buckets carrying auto-remediate=true, and auto-remediate through SSM Automation when they fail.
  5. Remediation runs an AWS-managed SSM document, verified live against this account before use.
  6. A scheduled Lambda reads the pack's own compliance status daily and emails a digest — scoped to these three rules, never the account's other ~300.
  7. A failed reporter invocation lands in a 14-day dead-letter queue that alarms.

Design decisions

Tag-scoped opt-in, enforced by Config itself. An untagged bucket is never flagged non-compliant, so remediation never fires for it. No custom code decides this — the scope is the control.

Notify, never invent. required-tags does not auto-tag. A human has to supply the actual cost-center value; automation only reports what is missing.

A conformance pack, not standalone rules. A pack is self-contained. Build standalone Config rules or a pack — never both for the same rule.

Implementation

A Config recorder and delivery channel, a three-rule conformance pack, an SSM remediation role, and a scheduled reporter with its DLQ and alarm. The lab guide carries the full Terraform and the pack YAML.

Never hardcode a name AWS generates for you. Conformance-pack rule names get a real generated suffix — discover them at runtime rather than writing them down.

Security and Cost

Security

Tag-scoped opt-in, enforced by Config alone. The two S3 rules only evaluate buckets tagged auto-remediate=true, via Config's native scope. An untagged bucket is never flagged, so remediation never fires for it, and no custom code decides that.

Native remediation substrate, not custom code. Both fixes are AWS-managed SSM Automation documents, verified live against this account before use.

Notify, never invent. required-tags never auto-tags a resource. Automation reports what is missing; a human supplies the value.

No silent failures. Failed reporter invocations land in a 14-day SQS dead-letter queue that alarms to SNS.

The guardrail that did not transfer. A tag-scoped IAM condition works for EC2 security groups and silently does nothing for S3 bucket-level admin actions. Verify per action rather than assuming a pattern carries.

Troubleshooting and Lessons

HCP's remote runners have no AWS credentials by default

Problem. The first plan on a brand-new workspace errored immediately: "No valid credential sources found".
Root cause. HCP's remote execution environment is not running inside the AWS account, so nothing hands it credentials.
Resolution. Two workspace environment variables enable the dynamic-credentials (OIDC) flow: TFC_AWS_PROVIDER_AUTH=true and TFC_AWS_RUN_ROLE_ARN.
Lesson. Obvious in hindsight, and it blocks every first run on a new workspace.

A tag-scoped IAM guardrail does not transfer between services

Problem. An IAM condition that correctly restricts EC2 security-group actions by tag had no effect on S3.
Root cause. S3 bucket-level admin actions do not evaluate the same condition key.
Resolution. Verify the guardrail per action rather than assuming the pattern carries.
Lesson. It fails open and silently — the policy is accepted, and simply does not constrain anything.

The account's only Config recorder was deleted mid-build

Problem. An apply broke because the recorder had vanished.
Root cause. An unrelated project's cleanup script removed the shared recorder. Nothing in this week's Terraform owned it at the time.
Resolution. This stack now owns its recorder outright.
Lesson. "Reuse the centrally-managed recorder" is only safe if you actually control it. This is also what made Week 15 necessary — nothing could say who deleted it.

Never hardcode a name AWS generates

Problem. Remediation could not find its rule.
Root cause. Conformance-pack rule names get a generated suffix.
Resolution. Discover them at runtime.
Lesson. A generated name is not a stable identifier.

Cleanup and Key Takeaways

Queue a destroy plan on week-12-dev in the HCP UI. This removes the conformance pack, the reporter Lambda, its schedule, SNS and DLQ, the SSM automation role — and the recorder itself, since this stack owns the account's only one.

Confirm nothing else depends on it first. Destroying this week takes AWS Config out of the account, and anything using Config as an evidence source loses it. Leftover test buckets clean up separately.

Key takeaways

  • A conformance pack is self-contained. It defines its own rules rather than wrapping externally-created ones — build standalone rules or a pack, never both for the same rule.
  • Config's scope is either-or. Resource type and tag filtering cannot combine in one rule.
  • Never hardcode a name AWS generates for you. Discover it at runtime.
  • A tag-scoped IAM guardrail does not automatically transfer between services. It works for EC2 security groups and silently does nothing for S3 bucket-level admin actions.
  • "Reuse the centrally-managed recorder" is only safe if you control it. Otherwise someone else's cleanup script is in your dependency chain.
