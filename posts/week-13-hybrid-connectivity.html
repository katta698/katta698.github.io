Lab Overview

The problem. Building an encrypted tunnel between two networks is the easy part. Both ends agree on ciphers, the tunnel comes up, and a dashboard turns green. Then a packet leaves a machine on one side headed for an address on the other, and the network has to answer a question nobody has answered yet: does this go down the tunnel, or out to the internet? Something has to put that answer in a route table. Type it by hand and it is correct until the day the other side changes — or until the tunnel dies, and the route keeps pointing at it with total confidence.

The objective. Build HA VPN between two VPCs, let BGP populate both route tables, then break one tunnel and measure how long the network takes to route around it.

Expected outcome. Two route tables neither side typed, each holding the other's subnet twice — once per tunnel. Kill one tunnel and the count halves, traffic keeps flowing, and no human touches anything. If the prefix only appears once, the second tunnel is not carrying it and the redundancy is nominal.

Deployment method. Terraform on HCP Terraform agents with no stored credentials — the workspace mints an OIDC token per run and exchanges it for a short-lived Google token, with separate identities for plan and apply. Built in Week 02; every week since rides on it.

Static routes versus BGP, and why it is not a style choice

A route table says: for addresses in this range, send the packet that way. For your own subnets it fills itself in. For anything beyond a tunnel, something has to add the entry.

You can type it — anything for 10.30.0.0/24, send down tunnel 1. Or the two routers can tell each other, continuously, which ranges they can reach. That conversation is BGP, and each side identifies itself with an ASN; there is a private range, 64512–65534, for cases like this.

The difference that matters is not convenience. BGP also withdraws routes. When a session drops, everything learned through it is removed from the table automatically, and traffic shifts to whatever is left. A static route cannot do that — it points at a dead tunnel exactly as confidently as a live one, and keeps sending traffic into a hole until a human notices.

So BGP is not an optional extra layered on top of HA VPN. It is the mechanism that makes the HA real. Two tunnels with static routes gives you two tunnels and an outage.

What "high availability" actually requires

Google's wording is specific: for the 99.99% SLA "there must be a tunnel from each of the two interfaces on the HA VPN gateway to the corresponding interfaces on the peer gateway." Two interfaces, two tunnels, two peer addresses.

And a single active interface does not get a reduced SLA — it gets none. That is worth knowing before someone builds one tunnel and calls it done.

One thing worth getting exactly right, because the loose version is everywhere: Classic VPN is not deprecated — but BGP on it is. Google deprecated dynamic routing for Classic VPN tunnels on 1 August 2025. Creating a Classic VPN tunnel that uses BGP is no longer supported; tunnels that already exist “will continue to function, but without an availability SLA”. Static routing on Classic VPN remains supported and keeps its 99.9% SLA.

Which means the specific thing this week is about cannot be built on Classic VPN any more. Not slower, not unsupported-but-working — you cannot create it. HA VPN is the only way to get a BGP session with Google, and that is a better reason to use it than any SLA table.

Architecture and Workflow

  1. A second VPC and subnet are created to stand in for a remote site, on a range that cannot overlap the hub's.
  2. An HA VPN gateway is created on each side, each with two interfaces and their own public IPs.
  3. A Cloud Router is created on each side, on different ASNs.
  4. Four tunnel resources are declared — two logical tunnels, each side declaring its own end — pairing interface 0 to interface 0 and 1 to 1.
  5. Each router gets an interface and a BGP peer per tunnel, addressed on link-local 169.254.x.x/30 ranges.
  6. The sessions establish, each side advertises its own subnet, and both route tables fill themselves in.
  7. One BGP peer is disabled. The routes learned through it are withdrawn, and the surviving tunnel carries the prefix.

Design decisions worth stating

Different ASNs on each side. Identical ASNs would make this an iBGP session, which does not re-advertise learned routes the way this topology needs.

The branch is a VPC, not another cloud. The roadmap called this week "cross-cloud", and the honest version is narrower: Google documents HA VPN topologies for on-premises gateways, Google Cloud VPCs and Compute Engine VMs, and no topology for a peer belonging to another cloud. A peer in the AWS lab is a genuinely different week, and it waits for one both windows can build together.

Prerequisites

  • A hub VPC (Week 04) with at least one subnet.
  • Keyless CI through Workload Identity Federation (Week 02).
  • Pipeline permissions on the platform folder. compute.networkAdmin was already there and covers networks, routers and VPN gateways. It does not cover firewall writes or instance creation, so this week added compute.securityAdmin and compute.instanceAdmin.v1.
  • Non-overlapping address space. BGP advertises these ranges; an overlap makes the route ambiguous.

Security and Cost

Security

  • The pre-shared key is generated, never typed. gen-psk.sh writes a random key into a gitignored tfvars file; no credential appears in this repository.
  • The probe VMs have no external addresses. They exist to be routed to, not reached from outside.
  • Firewall rules name the peer ranges explicitly rather than opening to anything that arrives over the tunnel. A tunnel being encrypted says nothing about what should be allowed through it.
  • Both VMs carry enable-oslogin and block-project-ssh-keys, because the organization's policies refuse to create them otherwise — see Troubleshooting.
  • No service account keys, as in every week of this lab.

Troubleshooting and Lessons

The pipeline could build the network but not the things in it

Problem: the apply created gateways, routers and all four tunnels, then failed with 403 on compute.firewalls.create and compute.instances.create.
Root cause: compute.networkAdmin covers networks, routers and VPN but not firewall writes; and Week 04 granted instanceAdmin on the workloads folder, not platform.
Lesson: a role named for a domain does not cover everything in that domain. The split between "the network" and "rules applied to the network" is a different role, and the same create-versus-modify boundary has now appeared in four separate weeks of this lab.

The organization refused to create the VMs

Problem: Error 412: Operation denied by org policy on both requireOsLogin and blockProjectSshKeys.
Root cause: Week 03 set those constraints and Week 04 promoted them to enforced. Any VM created afterwards must carry the matching metadata.
Why it had never happened before: the only other VM in this lab predates enforcement. It was created while the constraints were still in dry run, so nothing had ever been built under them. This was the first.
Lesson: a guardrail promoted after the fact is untested until something new arrives. The gap between "enforced" and "exercised" can be months.

The flag is --no-enabled, and there is no --disable

Problem: the failover script failed with unrecognized arguments: --disable.
Root cause: gcloud compute routers update-bgp-peer takes --enabled / --no-enabled.
Lesson: worth recording because the failure was safe by construction — the disable never happened, so nothing was left broken, and the restore in the finally block had nothing to undo. A script that degrades a control should be written so that failing early leaves the control intact.

Cleanup and Key Takeaways

Cleanup

terraform destroy removed everything this week created and left Week 04's hub VPC in place. Verified against the cloud rather than against state: zero tunnels, zero routers, zero gateways, zero instances, and the branch VPC gone.

Unlike Week 12's Cloud KMS key, nothing here survives a destroy and nothing keeps billing afterwards.

Key takeaways

  1. BGP is what makes HA VPN highly available. Two tunnels with static routes gives you two tunnels and an outage. The withdrawal behaviour — measured here at 3.1–3.6 seconds — is the entire difference.
  2. A single active interface carries no SLA. Not a reduced one. None.
  3. Four tunnel resources, not two. Each side declares its own end and each bills, so the hourly rate is double what the topology diagram suggests.
  4. A learned route is invisible in your code, which is the point and also the thing to remember when debugging. If a prefix is reachable and you cannot find it in your Terraform, that is BGP working.
  5. Enforced is not exercised. Two org policies set months ago blocked this build on their first real test, because the only VM that existed predated them.
