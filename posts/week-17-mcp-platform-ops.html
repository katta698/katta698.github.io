Lab Overview

On 30 August I opened a bill I did not expect and asked a simple question: what is running, what is it costing, and did I leave anything behind?

The problem. Answering it took eleven separate lookups across five systems — one for what I was charged, one for who changed what, one for what still existed, one for whether anything had alerted, one for what my infrastructure code believed. None of them talk to each other, and each required me to already know it held the answer. Every number had existed for days: a service billing $9.35 a day for a week, a budget alert fired and ignored, anomaly detection flagging eight cents and missing the sixty-one dollars next to it.

The objective. Build an MCP server that lets a model answer the question without knowing which six APIs to call, in what order, with what filters.

The outcome. It works, it costs $0.13, and writing up its own security model caught a claim about it I had published three times and never checked.

MCP, in one sentence: a protocol that lets a model call tools you define, where each tool has a name, a description and a schema — and the model decides when to call it.

A tool description is model input, not documentation. It is not text for humans that the model happens to see; it is the thing the model reads to decide what to do. Anything written there is read on every call.

Architecture and Workflow

  1. A client signs an HTTPS request with SigV4 and calls the Lambda Function URL.
  2. Lambda rejects anything unsigned before application code runs — the Function URL is set to AWS_IAM auth.
  3. The server exposes four tools, each mapping to exactly one read path into the account.
  4. Cost questions check the DynamoDB cache first, because Cost Explorer is metered per request and the model decides call frequency.
  5. A cache miss calls Cost Explorer, returns the answer and writes it back to the cache.
  6. Everything else — CloudTrail, Config, CloudWatch — is a free read, so it goes straight through.

Design decisions

IAM scoped per tool, not per server. Each statement maps to exactly one tool, so the policy reads as a list of capabilities rather than a permission surface.

A Function URL rather than API Gateway. It removes every idle charge and the entire Cognito surface. It also means an off-the-shelf MCP client speaking plain HTTP cannot connect — it gets a 403 before the protocol starts, because it has no idea how to sign an AWS request. For a personal account where the only caller is me, that trade is obviously right; for a platform team it is the first thing to revisit.

A cache in front of the one metered API. When a model decides how often to call something, a cent per request is an architectural constraint, not a rounding error.

Security and Cost

Security

No write on anything the server reports on. The only write in the role is dynamodb:PutItem against its own cache table. A model steered by a poisoned tool description can fill a cache; it cannot change the account. That turns a destruction risk into a disclosure one.

IAM scoped per tool, not per server, and the cache write scoped to one table ARN rather than DynamoDB generally.

AWS_IAM auth on the Function URL. Every request must be SigV4-signed by a principal allowed to invoke it; Lambda rejects the rest before application code runs.

Tool descriptions are treated as model input. They say what the tool answers and what it costs, and nothing else.

Permissions are the security model, not code. It would be easy to claim this server is safe because the code only reads. Code can be changed between reviews; a policy is checked by AWS on every call.

Troubleshooting and Lessons

I published a claim about my own security model that was not true

Problem. Three files — the handler docstring, the Terraform comment and the README — said the role holds no write action of any kind.
Root cause. I wrote it while designing. It was true of the design in my head, and I never re-read it against the thing I built. The fourth statement holds dynamodb:PutItem — a scoped write to the server's own cache, architecturally fine, but the claim was false.
Resolution. Rendering the policy as a screenshot and reading it. The accurate claim is narrower and still worth making: there is no write on anything the server reports on.
Lesson. The fix was not proofreading — it was rendering the artefact as evidence. Describing a policy lets you describe the policy you meant; showing it forces the one that exists.

The console would not show the proof

Problem. The IAM console lists a policy name and hides its body, so the screenshot that would prove the claim did not exist there.
Root cause. Chasing the console was the wrong instinct — the authoritative copy is the API's.
Resolution. Read the policy back from the API and render that.
Lesson. When the console will not show a thing, ask whether the console is the right source rather than how to make it cooperate.

One metered API changes the architecture

Problem. A model decides how often to call a tool, and Cost Explorer bills per request.
Root cause. Almost every AWS read is free, so the instinct is that reads are free. One is not.
Resolution. A DynamoDB cache in front of the only metered path.
Lesson. Know which reads are metered before you let something else choose the call frequency.

Cleanup and Key Takeaways

Queue a destroy from HCP, then verify against AWS rather than against the run status. The script checks Lambda, IAM, DynamoDB, alarms and log groups by name prefix, then does a tag search for Week=17.

That second check exists because of a specific failure. Week 12's teardown reported success and left two S3 buckets behind — a shell script had created them outside Terraform, so destroy had no idea they existed. A destroy run tells you Terraform removed what it knew about. It tells you nothing about what it never knew.

Key takeaways

  • The bottleneck was never the data. Every number I needed already existed; what was missing was a way to ask without knowing which API held the answer.
  • Know which reads are metered. When a model decides call frequency, one metered API changes the architecture.
  • A tool description is model input, not documentation the model happens to see.
  • Permissions are the security model, not code. Code changes between reviews; a policy is enforced on every call.
  • Render the artefact instead of describing it. Showing the policy caught a false claim I had written three times and read past twice.
