Lab Overview

Deploying to Kubernetes by hand does not scale past about one person. Somebody runs kubectl apply from a laptop, the cluster drifts away from what is in Git, and nobody can say with confidence what is actually running.

The problem. GitOps is the usual answer: you stop applying things, you commit, and a controller inside the cluster pulls the change and makes reality match. Argo CD is the tool most teams use. But AWS now runs Argo CD for you — the EKS Capability puts the controllers in AWS-managed infrastructure outside your cluster. Every tutorial online installs it with Helm onto your own nodes, because until recently that was the only option.

The objective. Run both, on one cluster, against one repository, and find out what actually differs.

The outcome. The operating model decides things that have nothing to do with price — and the two installations cannot coexist as cleanly as separate namespaces suggest.

GitOps in one sentence: Git holds what should be running, a controller continuously makes the cluster match, and nobody applies anything by hand.

Two words that look alike and are not. An Argo CD Application reporting Sync Unknown and Health Healthy has not found a problem — it has failed to look. "Unknown" is not "unhealthy", and confusing them is how a broken sync reads as a working one.

Architecture and Workflow

  1. One EKS cluster and one Git repository hold the desired state.
  2. The AWS-managed capability runs its controllers outside the cluster, with no pods of yours, authenticated via Identity Center.
  3. The self-managed Argo CD runs the identical project as pods on your own node group.
  4. Both watch the same repository with the same sync policy and the same application.
  5. Each reconciles the cluster toward Git, writing a tracking annotation on the resources it owns.
  6. Where both manage the same resource, the last writer takes the annotation and reports Synced; the other reports OutOfSync permanently.

Design decisions

Both installations, deliberately. A comparison is only worth reading if the thing being compared is the only thing that differs: same cluster, same repository, same application, same sync policy. What is left is the operating model.

Least privilege over the documented shortcut. Cluster-wide read so Argo CD can discover and health-check; write scoped to the single namespace it deploys into — not system:masters.

Identity Center rather than local Argo CD users. No shared admin password in a Kubernetes secret.

Troubleshooting and Lessons

The two Argo CDs cannot both own the CRDs

Problem. The first apply built the VPC, cluster, node group and capability, then failed on the Helm release: "CustomResourceDefinition applications.argoproj.io in namespace "" exists and cannot be imported into the current release".
Root cause. Note namespace "" — that is Kubernetes saying the object has no namespace, because it cannot have one. CRDs are cluster-scoped. Separate namespaces isolate Deployments, Services and configuration, and isolate nothing whatsoever about the type definitions they share. Creating the capability installs the CRDs; AWS documents it in one sentence in a list of five.
Resolution. The second installation defers to the first rather than adopting the objects.
Lesson. Helm's refusal is correct and worth understanding rather than working around.

Self-heal converges what it knows about

Problem. An out-of-band resource survived indefinitely under a controller with self-heal enabled.
Root cause. Self-heal reverts fields Git specifies and restores resources Git declares. It leaves alone any field Git never mentions, and never prunes a resource it never tracked.
Resolution. Treat "tracked" as the unit, and prune explicitly if you need it.
Lesson. "The cluster matches Git" does not mean "the cluster contains only what Git declares" — and that gap is where an out-of-band change hides.

Two controllers pointed at the same resources will fight

Problem. One Application reported OutOfSync permanently.
Root cause. The last writer takes the tracking annotation and reports Synced; the other sees a resource it believes it owns, annotated for someone else.
Resolution. Give each controller its own resources. There is no shared-ownership mode.
Lesson. The permanently-unhappy controller is reporting correctly; the problem is the arrangement, not the report.

Cleanup and Key Takeaways

Eleven checks, all clear. Two are worth calling out, because they are the ones that quietly survive a careless teardown:

  • The EKS Capability is an AWS resource, not a Kubernetes object. It bills hourly and is invisible to kubectl. A cluster that looks empty can still be charging.
  • A deleted NAT gateway keeps its tags. A tag sweep finds it long after it stops billing, so the script resolves its state before reporting — a cleanup check that cries wolf is one people stop reading.

Key takeaways

  • Namespaces do not separate CRDs. Two installations of the same operator in different namespaces still contend for one set of cluster-scoped type definitions.
  • "Unknown" is not "unhealthy". An Application reporting Sync Unknown and Health Healthy has failed to look, not found nothing wrong.
  • Self-heal converges what it knows about — and never prunes a resource it never tracked.
  • Two GitOps controllers on the same resources will fight, and the loser reports OutOfSync forever, correctly.
  • Price is the wrong axis. The capability is the cheapest line on the bill; the control plane and NAT gateway dominate either way. Choose on operating model.
