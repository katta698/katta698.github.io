Lab Overview

1. The Challenge — Why Fixed Budget Alerts Aren’t Enough

Your EC2 spend is normally $80 a month. This week it is running at $200 — 150% above normal. Your total bill is $280, well under the $500 budget whose alert fires at $450. Have you been told?

The problem. A budget threshold answers "have I spent more than X", which you have to know the right X for in advance, per service. Tripling your EC2 bill passes that test silently. A NAT gateway left running overnight added $35 in data processing charges here and raised nothing, because the total stayed under budget.

The objective. Ask a different question — "is this unlike me" — using Cost Anomaly Detection, which models expected spend per service per day, and turn what it emits into an email a person can act on.

The outcome. The pipeline works. Two of the four things that went wrong failed completely silently, which is the theme of the week.

  1. Catches what budgets miss Anomaly detection catches relative spikes — a service costing 3× its normal amount — even when the absolute dollar value is small.
  2. Immediate alerts, not end-of-month surprises IMMEDIATE frequency means the alert fires as soon as the anomaly is confirmed — typically within minutes of the cost spike starting.
  3. Root cause in the alert The alert payload includes the specific service, region, usage type, and linked account. You know where to look before you open the console.
  4. Zero ongoing maintenance The ML model updates itself continuously. One-time setup, permanent benefit. And it’s completely free.

Concepts to understand before starting

  • ML-based anomaly detection. The model needs 10+ days of data to build a reliable baseline. Don’t expect alerts on a fresh account immediately.
  • SNS fan-out pattern. Two topics: one receives raw JSON from AWS, the second delivers a formatted email. Lambda sits between them as a transformer.
  • OIDC federation. HCP Terraform authenticates to AWS using short-lived tokens — no static keys stored anywhere.
  • VCS-driven IaC. Push to GitHub → HCP plans automatically. Merge to main → HCP applies. No GitHub Actions Terraform steps needed.

Architecture and Workflow

The architecture uses two SNS topics by design. The raw-anomaly topic receives dense JSON from AWS — not human-readable. Lambda transforms it and publishes a formatted plain-text alert to the cost-alert topic, which delivers to email subscribers. This separation gives a clean extension point: add Slack, PagerDuty, or Teams as additional subscribers to the formatted topic later without touching the detection layer.

Implementation

Step 1 — Create the AWS OIDC provider and IAM role

AWS has to trust HCP first. This is a one-time manual bootstrap.

Register app.terraform.io as an OIDC identity provider, then create the role HCP will assume:

AWS CLI — one-time bootstrap

aws iam create-open-id-connect-provider \
  --url https://app.terraform.io \
  --client-id-list aws.workload.identity \
  --thumbprint-list <thumbprint>

aws iam create-role \
  --role-name hcp-terraform-role \
  --assume-role-policy-document file://trust-policy.json

JSON — trust-policy.json (scoped to this workspace)

{ "Effect": "Allow",
  "Principal": { "Federated": "arn:aws:iam::<ACCOUNT_ID>:oidc-provider/app.terraform.io" },
  "Action": "sts:AssumeRoleWithWebIdentity",
  "Condition": { "StringLike": { "app.terraform.io:sub": "organization:katta:*" } } }

Gotcha — org slug is case-sensitive

The organisation slug in the OIDC sub claim is lowercase, whatever case the UI shows.

Step 4 — SNS topic policy (the part everyone gets wrong)

Important

The publishing principal is costalerts.amazonaws.com, not budgets.amazonaws.com — see Troubleshooting.

HCL — SNS topic policy

resource "aws_sns_topic_policy" "raw_anomaly" {
  arn = aws_sns_topic.raw_anomaly.arn

  policy = jsonencode({
    Statement = [{
      Principal = { Service = "costalerts.amazonaws.com" }
      Action    = "SNS:Publish"
      Resource  = aws_sns_topic.raw_anomaly.arn
    }]
  })
}

Security and Cost

7. Security Best Practices

  • No static AWS credentials anywhere HCP Terraform authenticates via OIDC, minting short-lived tokens scoped to the workspace. No AWS_ACCESS_KEY_ID stored in HCP, GitHub, or anywhere else.
  • Workspace-scoped OIDC trust The IAM trust policy uses StringLike with the workspace name in the sub condition. Only the week-05-dev workspace can assume this role.
  • Lambda least-privilege IAM The execution role has exactly two permissions: sns:Publish scoped to the formatted alert topic ARN, and CloudWatch Logs write access scoped to its own log group.
  • SNS topic policy scoped to service principal Only costalerts.amazonaws.com can publish to the raw-anomaly topic. No IAM user, cross-account entity, or other AWS service can inject fake anomaly payloads.
  • CloudWatch log retention set explicitly Without an explicit retention_in_days, log groups retain logs indefinitely — an unbounded cost. This Lambda’s log group is set to 14 days.

Troubleshooting and Lessons

Problem. The monitor and the subscription were both created and no alert ever fired. No error in CloudWatch, nothing in the console.
Root cause. The SNS topic policy named budgets.amazonaws.com as the principal. Cost Anomaly Detection publishes as costalerts.amazonaws.com, and AWS drops a refused publish silently.
Resolution. Name the right principal.
Lesson. A topic policy that refuses a publisher fails closed and quietly. The only evidence is the absence of messages, which looks exactly like "nothing has happened yet".

Problem. Days passed with no real alert, even while running charges up deliberately.
Root cause. Not a fault. The detector needs enough spend history to build a baseline before it can call anything anomalous, and a new monitor has none.
Resolution. Prove the delivery path with a test event, and wait for the baseline for the detection itself.
Lesson. With anything that learns normal first, "no alert" is the expected state for a while. Test the pipeline and the detector separately, because only one of them can be tested today.

Problem. The function ran successfully and no email arrived.
Root cause. The subscription was still in PendingConfirmation. SNS does not deliver to an unconfirmed endpoint, and does not treat that as an error.
Resolution. Click the confirmation link.
Lesson. This is the second silent failure in the same build, both on the delivery side. Assert on the subscription's state, not on its existence.

Problem. Every plan failed with No Terraform configuration files found in working directory, for a directory that was plainly in the repo.
Root cause. Partly established. The HCP GitHub App's repository access was scoped to a different repository, which explains the clone having nothing in it. Granting access did not on its own fix it.
Resolution. Enabling "Include submodules on clone" is what broke the cycle. The repository has no submodules, so why that mattered is unconfirmed, and it is recorded here as what worked rather than as an explanation.
Lesson. A VCS-connected workspace also refuses terraform apply from the CLI entirely — once VCS is the source of truth, the run page is the only place an apply or a destroy happens.

10. Key Takeaways

  • costalerts.amazonaws.com is the SNS publisher principal for Cost Anomaly Detection — wrong principal causes silent failure with no error.
  • The ML baseline needs 24–48 hours on a new monitor. Test with Lambda test events immediately after deploy.
  • Two topics, not one. A raw topic for AWS to publish to and a formatted one for people, so Slack or PagerDuty can be added without touching detection.
  • HCP dynamic credentials eliminate static AWS keys entirely. 15 minutes of setup, zero ongoing rotation burden.
  • Confirm the SNS email subscription before testing. Messages to unconfirmed subscriptions are silently dropped.
  • VCS-connected workspaces fail in layered ways. GitHub App repo access, OIDC slug case and stale config ingestion all surface as the same empty-directory error.
  • Cost Anomaly Detection is completely free. The only reason not to have it in every AWS account is not knowing it exists.
