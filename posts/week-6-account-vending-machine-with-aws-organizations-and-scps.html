Lab Overview

A new team needs an AWS account. How do they get one, safely, without an engineer in the loop?

The problem. Done by hand it is three separate acts of remembering: create the account, attach the right guardrails, put it in the right place in the tree. Miss the second and the account is live with no ceiling on it.

Why not Control Tower. It automates exactly this, and enabling it is a heavy, largely irreversible step that provisions its own Log Archive and Audit accounts. This build is the same pattern without the permanent Landing Zone.

The objective. A ServiceNow ticket in, an account in the right OU with its guardrail already attached out, and the ticket closed with the new account id.

The outcome. Every step worked except the one that needed capacity: the organization was at its account limit, and the workflow's own failure path crashed before it could say so.

What You Need to Know — Skills & Tools

Two ideas carry the build. An OU is where policy attaches, and a service control policy sets a ceiling rather than granting anything. An account inherits that ceiling the moment it lands in the OU.

Architecture and Workflow

Why Nest Under an Existing OU Instead of the Root?

This Organization already had real, active accounts and Control-Tower-style OUs (Core-OU, Archived-Accounts, Workloads-OU) sitting at the root — leftovers from a Landing Zone that had been enabled and later decommissioned. Rather than scatter new Sandbox/Production OUs alongside that existing structure, this project nests them inside the existing Workloads-OU, as siblings of the existing Dev OU. Always read the current state of a shared resource like an Organization before assuming it's a blank slate.

Why a Separate Lambda per Pipeline Step?

Following the same action-dispatch pattern as Week 4's glue_trigger, account_creator handles both create_account and get_account_status via an action key, since they share the same boto3 client and IAM role. account_mover and status_notifier are separate because they need genuinely different IAM permissions — least privilege is easier to enforce when a Lambda's role only ever needs to do one category of thing.

Implementation

Step 1: Terraform Modules

Six Terraform modules: organizations, scp, iam, lambda, step-functions, and api-gateway. The dev environment wires them together, with the Organizations OU lookup done via a real data source rather than assumed:

HCL — Nesting Under an Existing OU 
data "aws_organizations_organizational_units" "root_children" {
  parent_id = data.aws_organizations_organization.current.roots[0].id
}

locals {
  workloads_ou_id = [
    for ou in data.aws_organizations_organizational_units.root_children.children :
    ou.id if ou.name == var.parent_ou_name
  ][0]
}

module "organizations" {
  source    = "../../modules/organizations"
  parent_id = local.workloads_ou_id
  ou_names  = var.ou_names   # ["Sandbox", "Production"]
}

Step 2: Service Control Policy

Prerequisite — Enable the SCP Policy Type First

Enable the policy type on the root once before applying anything below (see Prerequisites):

AWS CLI — One-Time Root Setup 
aws organizations enable-policy-type \
  --root-id <root-id> \
  --policy-type SERVICE_CONTROL_POLICY

# verify it took effect
aws organizations list-roots

The guardrail denies expensive instance types and restricts regions. Attached once to the OU, inherited by every account that lands there:

HCL — Sandbox Guardrail SCP 
resource "aws_organizations_policy" "sandbox_guardrail" {
  name = "sandbox-guardrail-scp"
  type = "SERVICE_CONTROL_POLICY"

  content = jsonencode({
    Version = "2012-10-17"
    Statement = [{
      Sid      = "DenyLargeInstanceTypes"
      Effect   = "Deny"
      Action   = ["ec2:RunInstances"]
      Resource = "arn:aws:ec2:*:*:instance/*"
      Condition = {
        StringLike = { "ec2:InstanceType" = var.denied_instance_types }
      }
    }]
  })
}

resource "aws_organizations_policy_attachment" "sandbox_guardrail" {
  policy_id = aws_organizations_policy.sandbox_guardrail.id
  target_id = var.sandbox_ou_id
}

Security and Cost

Security — Controls at Every Layer

🔒 SCPs as a Hard Ceiling

The Sandbox guardrail SCP can't be bypassed by IAM inside the vended account — not even by that account's root user. It's enforced at the Organizations level, above any policy the account itself could ever grant.

🔐 Per-Lambda Least Privilege

account_creator can only call CreateAccount/DescribeCreateAccountStatus. account_mover can only call MoveAccount/TagResource. Neither can do what the other does.

🔒 Webhook Authentication

Same HMAC-SHA256 validation pattern as every prior week — hmac.compare_digest(), not ==, to avoid timing attacks. Unsigned requests are rejected before Step Functions ever starts.

💾 Secrets in SSM, Not Code

ServiceNow credentials and the webhook secret live in SSM Parameter Store as SecureString, read at runtime — nothing in environment variables or source.

What's Missing for Production
  • The shared hcp-terraform-role currently has AdministratorAccess — broader than this pipeline actually needs; a production setup should scope it down
  • No SCP yet on the Production OU — only Sandbox has a guardrail attached
  • No automated account-quota monitoring/alerting before hitting the org account limit
  • No automated cleanup path for accounts that fail mid-vend and never get tagged

Cost

The vending pipeline itself is essentially free to run — the real cost consideration is what happens after an account is vended.

Troubleshooting and Lessons

Problem. The organization was not the blank slate the module assumed.
Root cause. It already held Control-Tower-style OUs and three SUSPENDED accounts, residue of a decommissioned Landing Zone.
Resolution. Nested the new OUs inside the existing Workloads-OU, found by data source rather than assumed.
Lesson. Read the organization before writing to it. A vending machine that only works on an empty org works nowhere real.

Problem. The workspace failed with lstat ../../modules: no such file or directory.
Root cause. A CLI-driven HCP workspace uploads only the directory Terraform runs from, so a module source above it can never resolve.
Resolution. Connected the workspace to the repository instead, with working-directory set to the environment path.
Lesson. Module layout decides which execution mode is available to you.

Problem. Attaching the SCP failed with PolicyTypeNotEnabledException.
Root cause. SERVICE_CONTROL_POLICY had never been enabled on the root, and Terraform creates the policy quite happily while the type is off.
Resolution. enable-policy-type, once. The provider has no equivalent resource.
Lesson. Creating a policy and being allowed to attach it are different questions, and only one of them appears in the plan.

Problem. When account creation failed, the execution reported FAILED and the ticket was never told.
Root cause. VendingFailed read $.status_result.failure_reason, which only the polling branch sets. With CreateAccount itself failing, the field did not exist and the handler died on States.Runtime.
Resolution. A NormalizeFailure pass state that both Catch blocks route through, mapping $.error.Cause into the expected field.
Lesson. The failure path needs its own test. This one had never run until the day it was needed.

Problem. The first end-to-end test returned ConstraintViolationException: You have exceeded the allowed number of AWS accounts.
Root cause. Ten accounts against the default limit — seven active, three suspended, and suspended ones still count.
Resolution. None on the day. Closing an account does not free the slot: it stays suspended for about 90 days before deletion, and counts throughout. The limit moves only by support request.
Lesson. Quota is a capacity question with a lead time in days. Ask for the headroom before the first ticket arrives, not after.

Takeaways — What I'd Do Differently

  1. Read live state first. Assuming a lab account is a clean slate nearly scattered new OUs beside an existing populated tree.
  2. Execution mode matters as much as the code. CLI-driven and VCS-driven workspaces differ in what they can even upload, which decides whether a module layout works at all.
  3. Catch blocks need their own test. The happy path reviewed clean while the failure path dropped the notification entirely.
  4. Quotas are infrastructure too. A vending system is only as good as the account quota behind it, and that quota moves on a support ticket, not an apply.
