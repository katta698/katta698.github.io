Lab Overview

An AWS account exists. Who is allowed to log into it?

The problem. Answered by hand, it is always answered the same way: an IAM user per person per account, an access key handed over, and no one place that knows who can reach what. Those keys do not expire, and they are the first thing an AWS security review asks about.

The objective. Define the access once — three permission sets, three groups — and let AWS provision the matching role into every target account. Then sign in as a real test user and see exactly what she gets.

The outcome. It works, and the roles appear in the target account without being declared there. One optional Terraform argument, left at its default, quietly makes the whole thing a no-op.

  1. Define Once A permission set (e.g. Engineers) is written once in Terraform, backed by an AWS managed policy and its own session duration.
  2. Group, Don't User People join a group (Engineers, ReadOnlyAuditors, BreakGlassAdmins) instead of getting individual per-account permissions.
  3. Assign Across Accounts Terraform assigns each group's permission set to every target account in one pass — AWS auto-provisions the matching IAM role in each one.
  4. Sign In Once Users sign in to a single SSO portal and federate into whichever account/role they're assigned — temporary credentials only, never a static key.

Architecture and Workflow

Why Groups Instead of Per-User Assignments?

Permission sets are assigned to groups, never to individual users. Adding someone to Engineers grants every account that group already has, with no Terraform apply per person.

Why a Cross-Product for Assignments?

Every group needs its permission set in every account, so the module builds the set as setproduct(keys(groups), target_account_ids). Add an account to the OU and the next apply assigns every group to it.

Implementation

Step 1: The identity-center Terraform Module

One module, six resource types, looped over a single groups map:

HCL — Cross-Account Assignment Cross-Product 
locals {
  assignments = {
    for pair in setproduct(keys(var.groups), var.target_account_ids) :
    "${pair[0]}-${pair[1]}" => {
      group_name = pair[0]
      account_id = pair[1]
    }
  }
}

resource "aws_ssoadmin_account_assignment" "this" {
  for_each = local.assignments

  instance_arn       = var.instance_arn
  permission_set_arn = aws_ssoadmin_permission_set.this[each.value.group_name].arn
  principal_id        = aws_identitystore_group.this[each.value.group_name].group_id
  principal_type      = "GROUP"
  target_id           = each.value.account_id
  target_type         = "AWS_ACCOUNT"
}

The target accounts are not hardcoded. They are looked up from Week 6's vended OUs with aws_organizations_organizational_unit_child_accounts, so adding an account to Sandbox or Production becomes a new assignment target on the next apply.

Security and Cost

Security — Controls at Every Layer

  • Least-privilege permission sets. Three distinct levels (ReadOnlyAccess, PowerUserAccess, AdministratorAccess) rather than one shared admin role handed to anyone who needs any access at all.
  • Shortest session for the highest privilege. BreakGlassAdmins gets a 1-hour session, deliberately shorter than the 4-hour Engineers one. Full-admin access should expire fastest.
  • No static credentials anywhere. Every session is federated and temporary. No IAM user and no access key was created in any target account, not even for the test user used to validate this.
  • Real emails stay out of git. terraform.tfvars is gitignored; the committed .example shows the shape only.
What's Missing for Production
  • MFA enforcement was relaxed to "Allow them to sign in" purely to unblock testing — must be reverted to requiring MFA registration before any real user gets one of these permission sets
  • No automated lifecycle for removing a user's group membership when they leave a team or the org
  • BreakGlassAdmins has no approval workflow or alerting on use — a real break-glass process should notify someone the moment that permission set is actually assumed
  • Permission sets use broad AWS managed policies; a production rollout should move toward narrower customer-managed or inline policies per role

Cost

IAM Identity Center, permission sets, groups, users, and account assignments are all free — so are the IAM roles Identity Center provisions into target accounts.

Destroyed: $0. Nothing in this week's build carries a per-resource cost — the only thing worth cleaning up deliberately is the test deviations (MFA setting, OU override), not billable infrastructure.

Troubleshooting and Lessons

Problem. The first plan created zero account assignments and reported success.
Root cause. The module derives its targets by listing the child accounts of named OUs, and Week 6's Sandbox and Production OUs existed but had nothing vended into them yet. An empty OU is not an error: it returns an empty list, and setproduct of three groups with zero accounts is zero assignments.
Resolution. Overrode target_ou_names to ["Dev"] through an HCP workspace variable, pointing at an older OU with one active account. A deliberate deviation, written into the README to be reverted once accounts exist in the intended OUs.
Lesson. A cross-product over a data source yields nothing at all when one side is empty, and Terraform calls that a successful plan. Assert the count.

Problem. Signing in as the Terraform-created test user returned "You are required to provide multi-factor authentication that you do not have" — for a user with no MFA device, and after the MFA setting had already been relaxed.
Root cause. Not established. It behaved like a stuck sign-in state left by an earlier blocked attempt rather than a policy being evaluated: relaxing the setting and waiting for propagation did not clear it.
Resolution. Used the admin-initiated Reset password on the user's detail page instead of the self-service "Forgot password?" flow. That path issued a fresh credential and the block disappeared.
Lesson. Identity Center users created by Terraform have no password and no MFA device, and there is no Terraform equivalent of "send the invitation". The first sign-in is a manual step, and the admin path is the one that behaves.

Problem. All three permission sets were assigned to the target account, but the test user's portal showed only Engineers, which looked like two assignments having failed.
Root cause. Not a fault. The portal scopes by the signed-in user's own group membership, not by everything assigned to the account, and the test user was only in Engineers.
Resolution. None needed; confirmed against the assignment API, which listed all three.
Lesson. The portal and the API answer different questions. Check the one that reports configuration before concluding the configuration is wrong.

Takeaways — What I'd Do Differently

  1. Groups scale; per-user assignments do not. Onboarding becomes a group-membership change rather than a Terraform apply, so the access model scales independently of headcount.
  2. Verify the auto-provisioning. The account-side roles are real, auditable resources. Checking them inside the target account, rather than trusting the plan output, is what confirmed the pipeline end to end.
  3. "Not showing up" is not always a fault. The portal scopes by group membership. Checking the assignment API first saved a wrong fix.
  4. Document deviations rather than hiding them. Testing against a live account meant diverging from the stated design twice; both are written into the README as reversible.
